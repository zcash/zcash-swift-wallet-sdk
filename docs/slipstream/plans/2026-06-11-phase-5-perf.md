### T5.2 — Adaptive scan sub-batching (time-targeted commits; fetch chunks unchanged)
Decouple the SCAN call size from the FETCH chunk size: `scan_chunks` splits each received chunk into sub-batches sized by a time-feedback controller, so weak devices commit (and surface progress) every few seconds while fast devices behave exactly as today.
- Pure controller: `fn next_batch_len(prev_len: u32, prev_elapsed_ms: u64, target_ms: u64, min: u32, max: u32) -> u32` — proportional adjust `prev_len * target/elapsed`, clamped; unit tests (fast-device growth, slow-device shrink, clamps, zero-elapsed guard). Constants: `TARGET_BATCH_MS = 3_000`, `MIN_BATCH = 1_000`, `MAX_BATCH = chunk len` (i.e. never exceeds a fetch chunk), initial = full chunk (fast path identical to today: one batch per chunk → behavior unchanged on fast hardware).
- Treestate threading at INTRA-chunk boundaries: from_state for sub-batch N+1 must be the server treestate at the sub-batch boundary. Generalize the existing prefetch: when the controller decides the next batch ends at height H (< chunk end), spawn the treestate prefetch for H (same client.clone() pattern); the existing chunk-boundary prefetch is the degenerate case. RPC cost: ~1 per ~3s on weak devices, fully hidden behind scanning; zero extra on fast devices. NOTE the scan loop's `from_state` bookkeeping must stay exact (assert from_state.height+1 == batch start — upstream enforces).
- Apply ONLY to production `scan_chunks` (darkside `scan_chunks_from_treestate` keeps whole-chunk batches — synthesized states can't split mid-chunk; add a comment).
- Tests: controller unit tests; existing suites green; darkside `--no-run` compiles.
- Commit: `[#1755] slipstream: adaptive scan sub-batching with time-targeted commits`
