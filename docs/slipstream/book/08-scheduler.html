8. Scheduler & Spend-before-Sync

Estimated reading time: 15 minutes

1-minute summary

The scheduler is the engine's outermost loop — the layer between the FFI polling surface and the scan pipeline. Its one job is to convert a list of suggested scan ranges into sequential fetch+scan passes, track progress in a way that is safe to read from Swift on any thread, and signal when the wallet has reached a spendable state. The key insight is that the scheduler has almost no intelligence of its own: all decisions about what to scan, in what order, and when to stop come from suggest_scan_ranges inside the upstream WalletDb (D2 — "upstream brain, Slipstream body"). The scheduler owns only the orchestration loop, the progress counter ledger, and the reorg recovery arm.

suggest_scan_ranges as the single brain

Every iteration of the outer scheduler loop begins by calling wallet.suggest_scan_ranges() and scanning whatever the upstream library recommends. This is design decision D2 in full effect: the engine never maintains its own scan-range state, never decides what the next block height is, and never hard-codes the order of priority classes. If upstream changes its priority ordering, the engine automatically inherits the new behavior.

The library currently returns ranges in priority order: ChainTip first, then Historic in reverse-chronological order. The engine iterates through them in the order returned:

// scheduler.rs:95–115 (simplified structure)
loop {
    let ranges = wallet.suggest_scan_ranges()?;
    if ranges.is_empty() { break; }

    p.begin_pass(handle);
    let sum: u64 = ranges.iter().map(|r| r.block_span()).sum();
    p.set_pass_total(scanned_so_far + sum);

    for range in &ranges {
        run_range(ctx, range, &p, wallet, config).await?;
    }
}

ChainTip-first SbS semantics

The first range returned by suggest_scan_ranges (when one exists) carries ScanPriority::ChainTip. This is the most-recent unscanned block window. Slipstream scans it before any historic range, which means the wallet discovers the most-recent incoming notes — and therefore becomes spendable — before it finishes the historical backfill. This is the Spend-before-Sync property.

When the ChainTip range scan completes, the scheduler latches the spendable flag (scheduler.rs:306–310):

// scheduler.rs:306–310 — spendable latch
if range.priority == ScanPriority::ChainTip {
    p.set_spendable(handle);
}

set_spendable atomically stores 1 in Progress.spendable_hint and never resets to 0 (events.rs:113–115). Swift reads this field via snapshot() and propagates it to the wallet UI as the "wallet ready" signal. The field name is spendable_hint — "hint" because the engine cannot certify that all prior balance is recovered; it means only that the most-recent unscanned range has been scanned.

Progress counters: ratio vs. monotonic-delta split

The Progress struct (events.rs:20–49) holds nine AtomicU64 fields. They divide cleanly into two groups that have different reset behaviour:

FieldKindSemantics
scanned_blocksratioBlocks scanned in current pass.
fetched_blocksratioBlocks fetched in current pass.
pass_total_blocksratioTotal blocks in current pass denominator.
current_range_endratioEnd height of the scan range currently in progress.
spendable_hintlatch0 until ChainTip range completes; 1 thereafter (never resets).
enhanced_txsmonotonic-deltaCumulative transactions enhanced since the sync handle was created.
ranges_completedmonotonic-deltaCumulative ranges finished since the sync handle was created.
reorgs_recoveredmonotonic-deltaCumulative reorg recoveries since the sync handle was created.

Why the split? A ratio counter produces a percentage for a progress bar: scanned_blocks / pass_total_blocks × 100. But a ratio is only meaningful within one pass — it must reset to zero when a new pass begins. A monotonic delta counter is meaningful across passes: "how many transactions have been enhanced since the sync started" should keep accumulating, not reset when the scheduler opens a new pass. Conflating the two leads to either a progress bar that jumps backwards or a transaction count that resets to zero.

begin_pass (events.rs:144–150) resets only the ratio fields and updates the pass start timestamp; it leaves the delta counters alone:

// events.rs:144–150 — begin_pass resets only ratio counters
pub fn begin_pass(&self, handle: u64) {
    self.scanned_blocks.store(0, SeqCst);
    self.fetched_blocks.store(0, SeqCst);
    self.pass_total_blocks.store(0, SeqCst);
    self.current_range_end.store(0, SeqCst);
    // enhanced_txs, ranges_completed, reorgs_recovered NOT touched
    self.pass_start_ms.store(now_ms(), SeqCst);
}

The 0→100→60% snap-back lesson

An early version of the scheduler (set_pass_total before the T6.5 fix) used fetch_add to accumulate the denominator: first one range would add its block count, then a second range would add the next block count. This produced a correct final denominator — but only at the end of the pass. During the first range, the denominator was artificially small (only the first range's block count), driving the apparent percentage past 100%. When the second range started and added its block count, the percentage snapped back to a smaller number.

Observed on user's iPad A10, pre-fix

STATE.md T6.5 session notes: a user observed a progress bar reaching "100%" before the scan visibly completed, then snapping back to 60% when the second range started. Root cause: add_pass_total(first_range_blocks) called at pass-begin; add_pass_total(second_range_blocks) called only when the second range was reached. Fix: compute the full-pass sum before the loop and call set_pass_total(total) (STORE semantics, not accumulate). This is why set_pass_total is a STORE and the function is doc-commented as a deliberate fix.

The corrected code (scheduler.rs:122–132) computes the denominator once per pass:

// scheduler.rs:122–132 — whole-pass denominator (F1 fix)
let scanned_so_far: u64 = ranges.iter()
    .take_while(|r| r.end <= already_scanned_to)
    .map(|r| r.block_span())
    .sum();
let sum_remaining: u64 = ranges.iter()
    .skip_while(|r| r.end <= already_scanned_to)
    .map(|r| r.block_span())
    .sum();
p.set_pass_total(scanned_so_far + sum_remaining, handle);
// set_pass_total is STORE (overwrite), not fetch_add — prevents snap-back

Pass lifecycle: begin_pass and the handle-vs-pass boundary

A pass is one iteration of the outer suggest_scan_ranges loop. Passes are numbered by the scheduler but not exposed to Swift. A handle is the caller's view: one SyncHandle object that persists across all passes until the sync completes or is cancelled. The distinction matters for the counters:

  • Ratio counters are per-pass: they reset on each begin_pass call so the progress bar shows the current pass's progress, not the cumulative scan progress since the beginning of time.
  • Delta counters are per-handle: they accumulate across all passes so callers can detect "something happened" even across a reorg recovery that forced a new pass.

Per-range enhancement

Enhancement (fetching full transaction details) runs at three interleave points within the scheduler loop (see chapter 9 for the detail). The per-range point fires after each scan range finishes (scheduler.rs:325–351):

// scheduler.rs:325–351 (simplified)
run_range(&range).await?;
p.add_ranges_completed(1, handle);

// non-fatal per-range enhancement
if let Err(e) = run_enhancement(&mut wallet, &p, handle).await {
    warn!(err = ?e, "per-range enhancement failed (non-fatal)");
}

The call is non-fatal: an enhancement failure (gRPC timeout, server error) is logged and counted but does not abort the scan. Enhancement state is preserved between interleave calls by the upstream WalletDb — the next interleave call will pick up where the last one left off. This design prevents an unstable server from blocking an otherwise healthy scan.

ranges_completed as a boundary signal

Swift callers use snapshot().ranges_completed as a "something significant happened" signal. Each time a range completes, the counter increments monotonically. A caller that caches the last-seen value can detect new completion events by comparing against the current snapshot without needing the engine to push an event. This is consistent with the D8 (poll-based) design — the engine publishes no callbacks; the Swift layer polls on a timer.

Why not expose the range count?

The total number of ranges (denominator) is not exposed directly because it changes mid-pass: suggest_scan_ranges is called once per pass, and a reorg recovery can produce a new pass with a different set of ranges. Exposing a denominator that can change unexpectedly would complicate the Swift UI. Instead, Swift uses scanned_blocks / pass_total_blocks for the progress percentage and ranges_completed for discrete completion events.

Reorg recovery arm

When the scan pipeline returns a ScanContinuity { at } error, the scheduler's reorg arm catches it (scheduler.rs:207–264). The mechanics are described in chapter 10; the scheduler's role is bounded:

  • Increment reorgs_recovered (monotonic delta — persists across passes).
  • Apply a jittered backoff (reorg_backoff_ms = consecutive * 500ms, max 3s) to reduce hammering a load-balanced cluster during tip desync.
  • Guard against infinite loops: if consecutive >= MAX_CONSECUTIVE_REORGS (5), the recovery arm returns a hard error instead of retrying. This bound is a compile-time assert (scheduler.rs:31–35), not a runtime check.
  • On retry, call begin_pass to reset ratio counters — the progress bar should reflect the recovery pass, not the aborted pass.

Known limitations

Honest gaps
  • In-foreground tip-following (DONE, T8.1): after the scheduler runs to completion, sync_body enters a jittered 10–30 s probe loop and re-runs a keyless catch-up pass whenever the server tip advances, so post-sync balance updates no longer require the Swift layer to re-trigger a sync call. (See ch.19.)
  • Mempool (0-conf) detection (DONE, T8.2): between follow passes the engine holds a mempool stream and surfaces wallet-relevant pending transactions 0-conf; the wallet's own outgoing spends appear there before mining. (See ch.19.)
  • Progress percentages are pass-scoped: a user watching the progress bar will see it reset between passes (e.g., after a reorg recovery). The "snap-back" fix (T6.5) addresses within-pass jumps, but cross-pass resets are intentional and documented — the Swift layer is expected to show a "reorg detected" message rather than trying to continue the prior percentage.
