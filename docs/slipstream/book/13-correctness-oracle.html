13. Correctness & the Golden Oracle

1-minute summary · reading time ≈ 12 min

The oracle answers one question: does the Slipstream persistence path write the exact same bytes into data.db as the upstream reference path? It does this by running both paths on the same input and calling semantic_diff on the result. This chapter explains how the differ works, why it cannot return a false "IDENTICAL" verdict, what the determinism baseline revealed, how the single allowlist entry was approved, and what three levels of testing the oracle has passed. It ends with an honest account of what "VERDICT IDENTICAL" does not prove.

13.1 The D3 obligation

Decision D3 (locked 2026-06-10) states that Slipstream must write a data.db that is byte-identical to what upstream zcash_client_sqlite would produce for the same blocks. The reason is practical: the upstream wallet brain (spend path, summaries, key derivation) continues to operate on the same database. Any silent divergence would corrupt spend state or balances without any error surfacing at write time.

The golden oracle is the enforcement mechanism. It is not a post-hoc audit tool — it is a gate that every significant persistence change must pass before shipping. Three passes at increasing scale are required: hermetic synthetic (always-green), darkside with real notes, and mainnet.

13.2 The differ design

The semantic_diff function in oracle.rs compares two wallet databases as canonical row multisets. The key design choices and their rationale:

ChoiceRationale
Row multisets, not ordered setsSQLite has no guaranteed row order without ORDER BY; insertion order differs between paths. A multiset comparison is order-independent and detects duplicates.
Schema unionTables are collected from both databases: UNION(tables_a, tables_b). A table present in one DB but absent in the other shows up as a full-table diff — a missing table cannot be silently skipped.
Views and indexes excluded structurallyThe query SELECT name FROM sqlite_master WHERE type='table' AND name NOT LIKE 'sqlite_%' selects only tables. Views and indexes are not in that result set and are never compared — they are derived objects whose correctness follows from the underlying table data.
Canonical value encodingEach column value is serialised to a deterministic string: NULL, integers as decimal, reals via format!("{r:?}"), text as '...', blobs as x'hex'. This prevents false-positive diffs from type coercions.
Allowlist applied at column enumerationColumns in ALLOWLIST are filtered out before any row is read. Every row in every non-allowlisted column must match.

13.3 Why the differ itself is trusted: four mutation tests

The differ is itself tested against injected defects. Each test verifies that a specific category of divergence is caught — that a "VERDICT IDENTICAL" result cannot be a blind spot for that class of defect. The four mutation tests in oracle.rs are:

Test nameDefect injectedWhat it proves
identical_dbs_diff_clean Same rows inserted in different order into two DBs A clean verdict on genuinely identical content; insertion order does not create false diffs
row_delta_is_detected One column value changed in one DB ("y" → "z") Any single-row, single-column mutation is caught; the differ cannot return IDENTICAL when rows differ
duplicate_row_multiplicity_is_detected A row duplicated in one DB but not the other Multiplicity matters; the multiset semantics are enforced (a row count of 2 vs 1 is caught)
missing_table_is_detected Table u present in A, absent in B Schema union is enforced; a table entirely missing from one side surfaces as a diff, not a silent skip
What these tests prove together

If any of the following happened in production — a row inserted in one path but not the other; a column value diverging; a row appearing twice in one path; an entire table missing from one path — the oracle would return a non-clean verdict. A "VERDICT IDENTICAL" result cannot be caused by these four failure modes.

13.4 Determinism baseline and the allowlist protocol

Before any oracle comparison between paths can be trusted, the upstream path itself must be deterministic. If running upstream twice on the same input produces different databases, "VERDICT IDENTICAL" would be vacuously unsatisfiable.

Test upstream_path_is_deterministic in oracle.rs establishes this baseline: the same 30 synthetic blocks are scanned through the upstream path (no sparse facade) into two separate wallet directories; the resulting databases are diffed. The test asserts the diff is clean.

When this test was first run (T6.2), it revealed exactly one nondeterministic column: accounts.uuid. This column holds a random version-4 UUID generated at account-import time by zcash_client_sqlite-0.21.0/src/wallet.rs:464 — let account_uuid = AccountUuid(Uuid::new_v4()). It is a stable per-account opaque identity, not part of any scan output, and it varies between any two imports of the same key into separate databases.

The allowlist protocol

Adding a column to ALLOWLIST is a deliberate, auditable act. The protocol requires:

  1. Reproduction: the nondeterminism must be confirmed by the determinism baseline test actually failing on the column.
  2. Upstream write-site citation: the code responsible for generating the nondeterministic value must be identified and cited in the allowlist comment.
  3. Decision-log entry: a record must be appended to STATE.md explaining the allowlist rationale.

The allowlist currently has exactly one entry:

pub const ALLOWLIST: &[(&str, &str)] = &[("accounts", "uuid")];

The comment in oracle.rs:19–27 cites the write site verbatim. All scan tables — blocks, sapling_tree_shards, orchard_tree_shards, sapling_tree_checkpoints, orchard_tree_checkpoints, nullifier_map, tx_locator_map, scan_queue, and the rest — are clean with no allowlist entries.

13.5 Three oracle levels

Level 1 — Hermetic synthetic (always-green)

Two hermetic oracle tests live in oracle.rs and run in CI without any external server:

  • sparse_path_matches_upstream_on_synthetic_chain: 3,000 synthetic blocks with 3 Sapling outputs each, scanned in 1,000-block chunks. The checkpoint downgrade fires in every chunk (~900 downgrades per call) and the cross-chunk carry is exercised twice. Path A uses the upstream WalletDb directly; path B uses SparseFacade. Result: VERDICT IDENTICAL.
  • split_chunking_matches_upstream_on_dense_chain (T6.8-S): 80 "sandblasting-shaped" blocks (20 outputs each, ~2.5 KB wire/block) split by the production ChunkSplitter at a 6 KiB threshold — yielding 30+ sub-chunks with variable boundaries. Both paths receive the same boundaries. Result: VERDICT IDENTICAL. This test validates that the sparse path remains oracle-clean under the density and variable chunking of the spam era.

Level 2 — Darkside real-notes fixture

Test sparse_pipeline_matches_upstream_on_darkside_fixture in tests/darkside_oracle.rs stages the canonical 2-transaction mainnet fixture (heights 663,174 and 663,188), runs both paths against a local lightwalletd, and calls semantic_diff. It also asserts that path B finds 2 transactions and 200,000 zatoshi — confirming not just byte identity but correct note detection.

Level 3 — Mainnet 50,000 blocks

The CLI oracle subcommand ran:

Measured result (T6.4, 2026-06-11)

Server: zec.rocks:443 · birthday: 3,324,435 · tip: 3,374,443 · 50,009 blocks · 6 chunks

VERDICT IDENTICAL

Subsequent oracle runs at T6.8 and T6.8-H2 also returned VERDICT IDENTICAL, confirming the result holds across the full hardening+retry+sandblast-split engine builds.

13.6 Spendability gate

The darkside fixture test includes a belt-and-suspenders correctness check beyond the raw differ: after scanning with the sparse path, the wallet must report spendable == total == 200,000 zatoshi. This asserts that the scan result is not just byte-identical but spendable — the note decryption, nullifier tracking, and commitment tree state are all correct enough for the upstream spending path to recognise the notes as confirmed and available.

The confirmation policy follows the upstream Swift-exact confirmation count (10 confirmations by default). Because the darkside fixture places notes at heights 663,174 and 663,188 with the final scan height at 663,202, both notes have more than 10 confirmations in the scanned range, so spendable == total is the correct expectation.

13.7 Reorg oracle gates

Two additional oracle tests cover the reorg/truncate path:

  • reorg_recovery_produces_correct_tip_sparse (darkside): asserts that after a reorg is detected at height 663,201, truncated to 663,191, and re-scanned to 663,202 with the sparse path, the final tip is 663,202 — identical to the non-sparse recovery flow.
  • truncate_rescan_oracle_is_clean (darkside): performs a full sync with both paths (A=upstream, B=sparse), truncates both to height 663,174, re-stages, and re-scans from birthday. Final semantic_diff: VERDICT IDENTICAL. This proves the sparse path does not retain stale in-memory tree state across a truncate, because the per-range SparseTreeState is dropped on any error (including continuity errors that trigger truncation).

13.8 What "VERDICT IDENTICAL" does and does not prove

Honest limits — read before drawing conclusions

The oracle compares against upstream's behavior, not against the Zcash protocol specification. If upstream has a bug that causes it to write incorrect data, the oracle will return IDENTICAL because Slipstream replicates upstream's behavior — including any such bug. The oracle is a behavioral equivalence check, not a protocol conformance proof.

The oracle covers scanned-state tables. It does not cover app-level data (Zodl-specific tables), spend-path outputs created by createTransaction, or the correctness of the upstream scan kernel itself. Enhancement and transparent UTXO tables are covered by the oracle runs (they are in the 26 tables), but their contents on the mainnet oracle run reflect an empty test wallet (no transactions to enhance).

The oracle ran on specific fixtures and ranges. The synthetic chain has a fixed structure; the darkside fixture has 2 transactions; the mainnet run covers 50,009 blocks ending at tip 3,374,443 with a wallet that had no transactions. Behavior on wallets with many historical transactions, edge-case note commitments, or extreme densities outside the tested window is not covered by these specific runs.

"IDENTICAL" means the same bytes exist in both databases at the time of the oracle run. It does not mean the bytes are cryptographically correct relative to the chain, or that the commitment tree frontier is valid for future spending — that is guaranteed by the upstream brain, which Slipstream passes the same inputs it would receive in the non-sparse path.

Known limitations

  • The oracle has not been run on a wallet with a large number of historical shielded transactions (high note count). This is a planned but not yet executed test case.
  • The always-green hermetic oracle uses synthetic blocks with uniform density. Orchard-era density patterns have been tested in the mainnet run but not in a hermetic fixture.
  • The determinism baseline and allowlist were established on the mainnet network type. Testnet behavior is expected to be identical but has not been separately baselined.
