Introduction & Motivation

Part I — Overview  ·  estimated reading time: 8 minutes

1-minute summary

Slipstream began with a single question: why does our SDK take 64 minutes for what Zingo does in 11? This chapter tells that story, shows the measured results (iPad A10: 64 min → 8:30; both Zingo reference points beaten), and explains what Slipstream is — and what it deliberately is not.

The question that started this

In June 2026, a comparative benchmark on a 2016 iPad (A10 Fusion, 6th-generation) restoring a real 8-month Zcash wallet showed starkly different numbers across wallets. The old ZcashLightClientKit took 1 hour, 4 minutes, 26 seconds. Zingo took 11 minutes, 34 seconds. Zkool — built on hanh's warp-lineage engine — took 8 minutes, 53 seconds.

The same wallet, the same lightwalletd endpoint, the same Wi-Fi network. A 6.9× gap that grows on modern hardware (iPhone 16 Pro: our 16:55 vs Zingo 2:41, Zkool 1:13) is not a configuration problem. It is an architectural one.

That measurement triggered a systematic investigation, documented in docs/SYNC_PERFORMANCE_PROPOSAL.md. The root causes were clear:

  • Blocks were fetched serially, one tiny batch at a time, over a fresh gRPC connection per scan round.
  • Fetching and scanning were sequential: the CPU sat idle while blocks downloaded, then the network sat idle while CPU scanned.
  • The commitment-tree persistence path wrote ~10,000 checkpoint insertions per chunk only to prune most of them immediately — burning 95% of scan time in SQLite shard operations, not in trial decryption.
  • On A10-class hardware, this last bottleneck meant the wallet sat scan-bound at ~1,380 blocks/second while Zkool's warp engine runs at ~4,700 blocks/second using frontier math that never touches the full tree.

Slipstream is the answer. Not a rewrite of the wallet. Not a new file format. A replacement of the orchestration around the proven upstream cryptographic core.

What Slipstream is NOT

Scope

These are hard boundaries. Every claim of correctness in later chapters rests on them.

  • Not a new wallet format. Slipstream writes into the same data.db that zcash_client_sqlite manages. A wallet opened with Slipstream can be opened with the old SDK and vice versa. No migration needed; the schema is unchanged.
  • Not a protocol change. Slipstream speaks the same GetBlockRange / GetTreeState gRPC protocol to lightwalletd. It fetches more aggressively in parallel, but the wire format is identical.
  • Not a fork of wallet logic. Key derivation, note scanning, transaction construction, balance computation, spend paths — all of these come from the unmodified upstream librustzcash crates. Slipstream replaces only the orchestration around them.
  • Not a shipping product yet. As of this writing, Slipstream is a local-only prototype behind a compile-time flag in the Zodl wallet. It has not been pushed to any remote.

What Slipstream is

Slipstream is a new sync engine, written in Rust, that lives in the same Swift Package as the existing SDK (slipstream/core/) and can be swapped in transparently via a SlipstreamSynchronizer that implements the same Synchronizer protocol the app already uses. The key ideas:

  • Parallel fetch. Four concurrent GetBlockRange streams fetch blocks simultaneously from lightwalletd (vs. one serial stream). Each streamed chunk is split into byte-budgeted sub-chunks to handle density spikes (the 2022 sandblasting era reached 2.5 million outputs per 10,000 blocks).
  • Overlapped pipeline. Fetching and scanning run in parallel. While one set of chunks is being scanned, the next set is already downloading.
  • In-memory sparse tree. The commitment-tree (shardtree) operations run against an in-memory accumulator, flushed to SQLite in a single transaction per chunk. Checkpoint-downgrade removes the churn of ~9,900 transient checkpoint insertions per chunk, cutting scan time 5× on Mac and 1.8× on iPad A10.
  • Upstream brain intact. suggest_scan_ranges, scan_cached_blocks, the spend path, balance computation, and summaries are all unchanged upstream code — Decision D2.

The arc of the project

The numbers above did not arrive all at once. The chart below shows how a single key measurement — the iPad A10 restore time — evolved across the project phases that are now the chapters of this book. Each drop corresponds to a concrete architectural change, recorded in the STATE.md decision log.

Phase breakdown

The progression above maps to concrete work:

  • P0–P1 (Foundation + Transport): workspace skeleton, K=4 parallel GetBlockRange streams. Fetch became network-bound rather than connection-churn-bound.
  • P2 (Scan core): in-memory BlockSource, persistent WAL-mode WalletDb session, fetch∥scan pipeline. 50k blocks in 32s on Mac (G2).
  • P3 (Completeness): enhancer (concurrent get_transaction → decrypt_and_store), transparent/UTXO refresh, event/snapshot surface. Full differential oracle parity confirmed.
  • P4 (iOS Docking): C FFI surface, XCFramework (all three slices), SlipstreamSynchronizer. Real wallet restore: 158s vs 1,710s for the old SDK (10.8×) — M1 met.
  • P5 (Performance pass): per-stage instrumentation, adaptive sub-batching, whole-pass progress denominator, per-range interleaved enhancement. iPad time recorded at 16:50 under careful field conditions.
  • P6 (Sparse tree persistence): checkpoint-downgrade inside an in-memory ShardTree facade, oracle-clean (hermetic + darkside + mainnet IDENTICAL), default ON since T6.6. iPad 16:50 → 9:21 (auto) → 8:30 (manual-server). Sandblasting era made traversable via byte-budgeted chunk splitting (T6.8-S). Transient-error retries hardened (T6.8-H2).

Relationship to the old SDK

Slipstream is additive. The old sync pipeline in Block/CompactBlockProcessor.swift is unchanged; its test suite (OfflineTests, 475 tests) stays green at every commit. The Swift seam is a new file, Sources/ZcashLightClientKit/Slipstream/SlipstreamSynchronizer.swift, that conforms to the same Synchronizer protocol. Zodl selects between implementations via a feature flag; no app-surface change is required.

The Rust engine is a new workspace member (slipstream/core) that shares the same pinned zcash_client_sqlite / zcash_client_backend versions as the existing libzcashlc. One static library, one copy of the upstream crates — no symbol collision.

Known limitations

Current gaps (see chapter 19 for the complete list)
  • In-foreground tip-following (DONE, T8.1): after each pass, the engine enters a jittered 10–30 s probe loop; a server-tip advance triggers a keyless catch-up pass, cancelled by the existing AbortHandle on stop/free. The app no longer has to call start() again when new blocks arrive.
  • Mempool (0-conf) detection (DONE, T8.2): the engine holds a mempool stream between follow passes and surfaces wallet-relevant unconfirmed transactions 0-conf via decrypt_and_store_transaction; non-fatal (on cap it falls back to tip-polling).
  • Tor wired (DONE, T-Tor): when the host wallet enables Tor, the engine bootstraps its own arti client and routes wallet-identifying gRPC calls over isolated Tor circuits while the bulk block download stays direct — privacy parity with the old SDK at full sync speed. See chapter 15.
  • A10 sandblasting era: the spam era (~1.70M–2.00M blocks) is now traversable on Mac (84,964 blocks / 43.2M outputs validated). Device memory budgets on A10-class hardware (2 GB) need dedicated tuning before a birthday-935000 full restore is safe on device.
  • iPhone 16 Pro Zkool gap: Slipstream on iPhone 16 Pro is 1:35 vs Zkool's 1:13. The remaining lever is the decrypt-kernel track (L4a — the column-oriented ECDH kernel parked, awaiting a seam design).
  • LOCAL-ONLY: this prototype has never been pushed to any remote. No public release, no Android port, no productization decision made.
