18. Test & Verification Matrix

Part V — Evidence & Process  ·  estimated reading time: 12 minutes

1-minute summary

Slipstream maintains seven distinct test suites: slipstream-core unit tests (~119 hermetic), slipstream-cli tests (19), the stress binary (1 test, 120 joins), the hermetic oracle set (7 cases including dense/split, determinism, and mutation tests), darkside serial integration (10 named tests), OfflineTests (475 total, including 56 Slipstream-specific tests), and clippy-zero on both feature sets. This chapter gives each suite a row in the verification matrix, names exactly what failure class each suite would catch, lists the 10 darkside tests by name, gives the exact commands from CONVENTIONS.md, and explains the always-green discipline that ties commits to test state. It ends with the landmine list.

18.1 The always-green discipline

Every commit in the slipstream branch must contain: the work, its tests passing, and a STATE.md update. The unit of resumability is the commit — not the PR, not the day. The rule from CONVENTIONS.md:

Always-green commands (before and after every commit) 
cargo test -p slipstream-core -p slipstream-cli      # engine tests (fast)
swift test --filter OfflineTests                      # old SDK untouched (CI parity)

The cargo line runs before and after every commit. The Swift line is required at every phase gate and whenever a commit touches anything outside slipstream/ + docs/. Pure slipstream-internal Rust commits may skip it.

Heavier checks run when the touched area demands it:

# After any Cargo/workspace/FFI change:
./Scripts/init-local-ffi.sh --macos-only

# Darkside integration — SERIAL ONLY — needs local lightwalletd:
cargo test -p slipstream-core --features darkside \
  -- --ignored --test-threads=1
Darkside SERIAL-only warning

The darkside lightwalletd server carries shared state. Running darkside tests in parallel causes race conditions where one test's ResetDarkside call interferes with another test's staged chain. Always use --test-threads=1. This is the most common source of spurious darkside failures in new sessions.

18.3 The ten darkside tests by name

These tests require a locally-running lightwalletd in darkside mode (see §18.4). They are gated behind #[ignore] + the darkside feature flag so plain cargo test stays hermetic. At HEAD they are 10/10 serial, verified at every phase gate.

#Test nameSource fileWhat it verifies
1 live_lightd_info_smoke src/grpc.rs Basic connectivity — lightwalletd responds to GetLightdInfo on the darkside endpoint. If this fails, all other darkside tests will fail too.
2 sparse_pipeline_matches_upstream_on_darkside_fixture tests/darkside_oracle.rs Oracle: stages the TX_MAINNET_BLOCK_URL + 663174/663188 fixtures twice; runs Path A (upstream) and Path B (sparse) and calls semantic_diff. Verifies sparse tree produces byte-identical output on real fixture transactions.
3 truncate_rescan_oracle_is_clean tests/darkside_oracle.rs Oracle under reorg/truncate: full sync on A and B, truncate both to height 663185 (snaps to 663174 — nearest checkpoint), re-stage, re-scan from birthday, semantic_diff CLEAN. Proves checkpoint-downgrade survives truncate+rescan cycles.
4 reorg_recovery_produces_correct_tip tests/darkside_reorg.rs Before-reorg chain at 663200 → detect ScanContinuity{at:663201} → truncate to 663191 → re-scan → assert max(block height) = 663202. Non-sparse variant.
5 reorg_recovery_produces_correct_tip_sparse tests/darkside_reorg.rs Identical flow to test 4 but with sparse=true. Verifies the reorg arm interacts correctly with the sparse ShardTree accumulator and checkpoint-downgrade.
6 fixture_funds_are_spendable_after_full_sync tests/darkside_sync.rs Spendability gate: after full sync of the TX_MAINNET_BLOCK_URL fixture, funds can be spent (the commitment tree is correctly built and the spent-note path is valid). This is the ultimate correctness check.
7 sync_enhancement_stores_raw_fields tests/darkside_sync.rs Enhancement correctness: after scan + enhancement, txs_stored==2 (exact), raw IS NOT NULL for both transactions, balance==200,000 zatoshi, no duplicates. Source: BalanceTests.swift:888-889 oracle.
8 sync_finds_fixture_transactions tests/darkside_sync.rs Basic end-to-end: build darkside chain with 2 known transactions (at 663174 and 663188), sync, assert found-tx count=2 and balance=200,000 zatoshi. The G2/G3 correctness oracle.
9 parallel_fetch_5000_blocks_in_order tests/darkside_transport.rs Parallel fetch correctness: stages 5000 blocks, runs K=4 fetch, asserts blocks arrive in height order with correct prev-hash chaining. Catches reorder-buffer regressions.
10 stage_apply_and_read_tip_roundtrip tests/darkside_transport.rs Transport smoke: stage blocks 663150..=663350, apply, read latest block height, assert==663350. Verifies the gRPC staging→apply→query round-trip (and the 2 s sleep needed for darkside propagation).

18.4 Running the darkside suite

Start lightwalletd in darkside mode in one terminal:

Tests/lightwalletd/lightwalletd \
  --no-tls-very-insecure \
  --data-dir /tmp \
  --darkside-very-insecure \
  --log-file /dev/stdout

Then in another terminal, run the darkside tests serially:

cargo test -p slipstream-core \
  --features darkside \
  -- --ignored --test-threads=1

The --test-threads=1 flag is not optional. The darkside server carries global state; two tests resetting or staging simultaneously produce race conditions that look like genuine test failures.

18.6 Landmines

Three known environment hazards from CONVENTIONS.md:

Single-slice landmine

./Scripts/rebuild-local-ffi.sh <arch> replaces the whole local XCFramework with only one architecture slice by design (for fast iteration). After using it, other-platform builds and tests fail with "framework doesn't exist". Restore all three slices with ./Scripts/init-local-ffi.sh. Slipstream work requires macOS (swift test), ios-sim (Zodl simulator), and ios-device (field runs). Cross-reference ch. 17 for the stale-framework incident this can cause.

SPM staleness landmine

After any local-FFI mode switch, swift test may fail with "package at .../LocalPackages cannot be accessed" — SPM's shared manifest cache replays a stale evaluation. Fix:

rm -rf ~/Library/Caches/org.swift.swiftpm/manifests && rm -rf .build

Nested-framework landmine (fixed in 2026-06-11, kept for archaeology)

An older version of init-local-ffi.sh used cp -R to install into an existing destination, which placed the new framework inside the old one. Stale slices at the top level were used silently. Fixed by adding rm -rf before install. If you ever see libzcashlc.xcframework/libzcashlc.xcframework/ nested inside LocalPackages/, the layout is corrupt: rm -rf LocalPackages && ./Scripts/init-local-ffi.sh.
