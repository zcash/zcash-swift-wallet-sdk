7. Sparse Persistence

Estimated reading time: 17 minutes

1-minute summary

This chapter tells the best engineering story in the Slipstream project: a feature that initially failed badly, failed honestly, and then succeeded spectacularly after a root-cause analysis revealed a completely different lever. The sparse-persistence path accelerates the scan kernel's commitment-tree writes by 5× by keeping the Sapling and Orchard ShardTrees in memory during a scan range, flushing the dirty delta to SQLite once per sub-chunk inside the same transaction as the row writes. The key insight was not the in-memory tree itself — it was the checkpoint downgrade: upstream's scanning path emits a Retention::Checkpoint marker for every scanned block (~10,000 per 10k-block chunk), but the ShardTree library immediately prunes all but the newest 100 back down. Building and then discarding 9,900 checkpoints per chunk was the real bottleneck. Downgrading doomed checkpoints before they enter the tree eliminated ~11× of the tree_ms cost. The path is default-on, oracle-verified identical to upstream across all 26 database tables, and guarded by a kill-switch flag.

The story: T6.3 NO-GO → T6.3b 5.05× reversal

The sparse-persistence idea was straightforward: instead of committing the ShardTree state to SQLite on every put_blocks call (one per sub-chunk), accumulate it in memory across all sub-chunks of a range and flush once at the end. This would replace N SQLite tree-write round trips with 1, cutting the per-chunk tree_ms cost dramatically.

The T6.3 spike implemented exactly this design: SparseFacade intercepts only put_blocks and routes it to an in-memory SparseShardStore; everything else delegates to the real WalletDb verbatim. The A/B measurement was unambiguous:

T6.3 result — NO-GO

STATE.md T6.3 session log, 2026-06-12: Run A (sparse=false) scan_s=38.25s / Run B (sparse=true) scan_s=39.82s / ratio=0.96 — sparse is 4% slower than baseline. Per-chunk attribution: rows_ms~300ms, tree_ms~6500ms, flush_ms~1ms. The flush cost was negligible (1ms, as predicted). The tree computation dominated — and was the same in both cases. The in-memory bet was correct about flush cost but wrong about tree construction cost.

The per-chunk breakdown was diagnostic: tree_ms ≈ 6,500 ms regardless of whether the tree lived in SQLite or memory. The bottleneck was not I/O — it was CPU. A deeper look at insert_tree in the shardtree library showed the cause: upstream's scanning code emits a Retention::Checkpoint { id } for every scanned block, but prune_excess_checkpoints immediately cuts the set back to the newest 100 ids after each insert_tree call. For a 10,000-block chunk, this means ~9,900 checkpoint structs are created, inserted, walked by the pruner, and freed — all per put_blocks call.

T6.3b tested the hypothesis: compute the post-prune cutoff before building subtrees, and downgrade all doomed checkpoints to their residue (Marked → Marked; everything else → Ephemeral) before inserting them into the tree. The result:

T6.3b result — GO (5.05×)

STATE.md T6.3b session log, 2026-06-12: Run A (sparse=off) scan_s=34.63s / Run B (sparse=on, downgrade=true) scan_s=6.85s / ratio 5.05×. Per-chunk attribution: tree_ms dropped from 6,500ms to 498–600ms (~11×); rows_ms ~280–320ms; flush_ms=1ms; downgraded ~6,200–6,800 per chunk. The T6.3b result exceeds the 1.5× GO threshold (and the [1.3, 1.7] ambiguity band) by a wide margin. The tree_ms reduction is ~11×; the full-pass scan_s reduction is ~5× because rows_ms (the SQLite row-writes, ~300ms/chunk) is now the dominant cost, not the tree. This matches device field measurements: iPad A10 9:09 (T6.8 run) vs the expected pre-sparse ~45 minutes.

The WalletWrite facade: intercepting only put_blocks

SparseFacade (persist.rs:1116–1189) is a struct that holds two borrows: &mut Db (the real WalletDb) and &mut SparseTreeState (the per-range in-memory tree state). It implements both WalletRead and WalletWrite by delegating every method verbatim to self.inner — except for exactly one method:

// persist.rs:1173–1175 — THE INTERCEPT (the only override)
fn put_blocks(&mut self, from_state: &ChainState,
    blocks: Vec<ScannedBlock<Self::AccountId>>) -> Result<(), Self::Error>
{
    sparse_put_blocks(self.inner, self.sparse, from_state, blocks)
}

This design minimises the diff with upstream: the scan kernel, continuity checks, note decryption, nullifier tracking, and balance computation all run against the real WalletDb. Only the commitment-tree write path is intercepted. The facade's error type is the same as WalletDb's (SqliteClientError), so all upstream error shapes — including the continuity ScanError that triggers reorg recovery — propagate bit-for-bit.

SparseShardStore: the in-memory tree

SparseShardStore<H> (persist.rs:101–155) implements the upstream ShardStore trait over four BTreeMaps:

FieldTypeSemantics
shardsBTreeMap<u64, LocatedPrunableTree<H>>In-memory shard trees (loaded + mutated during the range).
dirty_shardsBTreeSet<u64>Indices of shards mutated since the last flush.
checkpointsBTreeMap<BlockHeight, Checkpoint>Current checkpoint state (in memory).
db_checkpointsBTreeMap<BlockHeight, Checkpoint>Mirror of the SQLite checkpoint rows (for flush diffing).

The read-miss policy is deliberate and loud: if get_shard is called for an index that is known to exist in SQLite (tracked in db_shard_indices) but was not preloaded at seed time, it returns SparseStoreError::NotPreloaded instead of silently returning None. A silent miss would produce incorrect tree output without any error signal; failing loudly here is a D3 guard.

At range seed time (seed_sapling and seed_orchard, persist.rs:307–367), ALL shards are loaded from SQLite into memory. This is safe because complete subtrees are stored as a single root-hash node (typically a few hundred bytes each), so the total preload cost for a wallet with thousands of shards is modest — a few hundred KB.

Checkpoint downgrade (T6.3b): the real lever

The core of the performance gain is doomed_checkpoint_cutoff and downgrade_doomed_checkpoints (persist.rs:1006–1075). The logic mirrors what upstream's prune_excess_checkpoints does, but runs it before the checkpoints enter the tree:

  1. Compute the retained set: the union of (already-stored checkpoint ids) ∪ (the frontier checkpoint id) ∪ (new batch's checkpoint ids) — exactly the set upstream would retain after pruning. The cutoff is the minimum of the newest 100 ids in this union.
  2. Downgrade doomed entries: any Retention::Checkpoint { id, marking } with id < cutoff is rewritten in-place: Marked marking survives as Retention::Marked; anything else becomes Retention::Ephemeral. This is the exact residue the prune cycle would leave anyway.
  3. ensure_checkpoints is preserved on full maps: the ensure_checkpoints cross-pool reconciliation (mirroring ll/wallet.rs:484–501) uses the pre-downgrade position maps, because a filtered map would remap an ensure-height whose nearest checkpoint lies below the cutoff onto the frontier position instead.

Per-chunk measurement (STATE.md T6.3b, 2026-06-12): downgraded ~6,200–6,800 checkpoints per 10k-block chunk; tree_ms dropped from 6,500ms to 498–600ms. The 11× reduction in tree_ms reflects the cost of the checkpoint-churn cycle in shardtree: roughly 10× the work for 10× more checkpoint inserts-then-prunes.

Per-pool rayon::join: parallel Sapling and Orchard trees

Within a single sparse_put_blocks call, the Sapling and Orchard commitment trees are completely independent — they hold different commitment types, reference different shard stores, and have no cross-pool data dependencies. The T6.8-L3a optimization parallelizes them via rayon::join (persist.rs:785–902).

The cross-pool dependency — ensure_checkpoints, which needs each pool's checkpoint position map to fill gaps in the other pool — is computed serially before the join. Everything inside the join closures is per-pool and safe to parallelize:

// persist.rs:785 — parallel per-pool tree pipeline
let (sap_result, orch_result) = rayon::join(
    || { /* sapling: downgrade → build_subtrees → insert_frontier → insert_tree → ensure */ },
    || { /* orchard: downgrade → build_subtrees → insert_frontier → insert_tree → ensure */ },
);
Measured 90/10 pool lopsidedness — T6.8 field run, iPad A10

STATE.md T6.8 session log: orch_tree_ms ≈ 5–11s/chunk vs sap_tree_ms ≈ 0.4–0.9s/chunk. The ~10:1 ratio reflects the Sinsemilla hash function (Orchard) vs Pedersen hash function (Sapling): Sinsemilla requires ~4× more operations per hash. The rayon::join win was that the hidden sapling time (previously blocking behind the serial orchard pipeline) is now fully hidden — explaining the L3a gain on device (−19s vs the stale-framework run).

The sub-attribution instrumentation (PoolTimers, persist.rs:1034–1048) splits each pool's pipeline into five time buckets: downgrade, build, frontier, insert, ensure. Per-chunk info! lines are logged in device logs:

// persist.rs:932–952
info!(rows_ms, tree_ms, sap_tree_ms, orch_tree_ms, flush_ms, downgraded, "sparse put_blocks");
info!(downgrade_ms, build_ms, frontier_ms, insert_ms, ensure_ms, total_ms, "sparse orchard tree split");
info!(downgrade_ms, build_ms, frontier_ms, insert_ms, ensure_ms, total_ms, "sparse sapling tree split");

The sub-attribution finding from T6.8-L3b (STATE.md): the dominant bucket is frontier_ms (~33% of orchard time), which is intrinsic to the shardtree merge_checked function in prunable.rs:277–352. This function recomputes root hashes on both subtrees at every recursion level without caching, even though the results are discarded (both sides are incomplete frontier path-trees). This is a known upstream limitation; a fix requires a fork or upstream PR (recorded in the roadmap as "L4b seam-blocked").

Checkpoint-window picture: why final tables match upstream

A key correctness claim is that after a full wallet restore through the sparse path, the sapling_tree_checkpoints and orchard_tree_checkpoints tables contain exactly the same rows as the upstream path. Here is why:

Flush atomicity

Each flush of the sparse tree delta to SQLite occurs inside inner.transactionally — the same transaction that writes the block metadata rows, note outputs, nullifiers, and scan queue update (persist.rs:539). This means a crash between sub-chunks leaves the database in a consistent state: either the last completed sub-chunk's rows and tree state are committed together, or neither is. There is no window where rows exist without a matching tree state or vice versa.

Crash consistency

SQLite WAL mode (enabled by upstream) provides durable commits. A crash mid-transaction leaves the WAL uncommitted; on restart, the database recovers to the last committed state — which is the start of the aborted sub-chunk. The scan pipeline resumes from the point where the ChunkQueue last released a permit, which is the last sub-chunk that was scanned and flushed. No data loss; no partial commits.

The kill switch

The sparse path defaults to sparse_persistence = true (since T6.6, oracle-clean). The EngineConfig field is the kill switch: setting sparse_persistence = false reverts to the upstream path. The SparseFacade is never constructed, and scan_cached_blocks writes directly to WalletDb. The CLI --sparse false flag exercises this (config.rs:93).

Known limitations

Honest gaps
  • frontier_ms seam-blocked: the merge_checked function in shardtree-0.6.2 performs redundant re-hashing that accounts for ~33% of orchard tree time. Fixing this requires patching the upstream library (recorded in the roadmap as a seam-blocked item). The current path is correct and oracle-verified; it is simply slower than it could be.
  • L2 row batching not implemented: put_blocks writes rows individually inside the upstream LowLevelWalletWrite boundary. Bulk-insert SQL would reduce rows_ms (~300ms/chunk) but requires access to internal upstream APIs not available via the public trait. This is the next performance lever after frontier_ms.
  • SparseTreeState scoped to one range: the in-memory tree is created fresh at the start of each scan range and discarded at the end (or on error). A reorg truncation always goes through the real WalletDb path; the sparse state is silently invalidated and will be re-seeded on the next range. This is correct by design and requires no explicit invalidation.
