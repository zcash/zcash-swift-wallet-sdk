10. Reorg Handling

Estimated reading time: 12 minutes

1-minute summary

A chain reorganisation invalidates blocks the wallet has already scanned. Slipstream detects reorgs at three independent layers, raises a structured ScanContinuity{at} error, and recovers by rolling the wallet state back — not by recalculating it. The key insight: tree states are never recalculated on recovery; they are rolled back to a stored checkpoint. Backoff prevents a load-balanced cluster's momentary tip-desync from burning through the entire recovery budget; a hard cap of five consecutive recoveries prevents infinite ping-pong. All claims are verified against darkside hardware.

The thing that makes reorgs tractable

When a chain reorganisation happens, every block above the fork height is invalid. The wallet has already scanned some of those blocks, storing notes, nullifiers, and — most importantly — shardtree state derived from their commitments. The naïve fix would be to undo that scanning by recalculating the shardtree from scratch. That would be catastrophically slow.

The real fix is a rollback: truncate_to_height in zcash_client_sqlite removes all data above the rewind height and rolls back the shardtree to the nearest stored checkpoint. Checkpoints exist precisely as rewind anchors — one is stored per block when scanning. After truncation, the wallet is in exactly the same state it was when it last committed below the rewind height. No recalculation. No reconstruction. A pure rollback to a known-good point.

Why this matters for auditors

The correctness guarantee is: post-recovery wallet state is byte-identical to what upstream's sync.rs would produce on the same chain. This holds because Slipstream uses the same truncate_to_height call, the same rewind formula (at − 10), and the same scan_cached_blocks kernel for the repair scan. The golden oracle (chapter 13) verifies this end-to-end: the sparse-mode reorg test truncate_rescan_oracle_is_clean checks all 26 wallet tables for equivalence after a round-trip truncate and re-scan.

Three detection layers

A reorg can be detected at three points in the pipeline, operating independently.

LayerMechanismError produced
Transport continuity The fetch pipeline's reorder stage (release_ordered in fetch.rs) runs a Continuity checker on every emitted sub-chunk. A prev-hash mismatch between consecutive blocks raises SlipstreamError::Discontinuity{at} immediately — before any data reaches the scanner. Discontinuity{at}
Wallet-level scan continuity Upstream's scan_cached_blocks checks that every new block's prev-hash matches what the wallet already stores, and that the shardtree size is consistent. A mismatch raises a ChainError::Scan with is_continuity_error() == true. The map_scan_error helper in scan.rs converts this to the structured ScanContinuity{at} variant. ScanContinuity{at}
Tip-priority verify ranges After each pass, suggest_scan_ranges may return Verify-priority ranges for blocks near the tip. These are scanned first (upstream contract: Verify is returned before ChainTip or Historic), re-detecting any fork that arrived since the last scan. Detected as wallet-level scan error on the verify range

In practice, the wallet-level layer (layer 2) fires most often for the standard reorg scenario: the server presents a longer chain, the fetch pipeline delivers the fork blocks in height order, and scan_cached_blocks sees the prev-hash mismatch at the first diverging block.

The structured ScanContinuity{at} type

Where previous sync engines used untyped strings or generic scan errors, Slipstream promotes the continuity break to a first-class error variant (error.rs:31):

/// Scan detected a chain continuity break (reorg) at the given height.
/// The scheduler's recovery arm truncates the wallet DB and re-suggests ranges.
#[error("scan continuity break at height {at}")]
ScanContinuity { at: u32 },

The at field carries the exact height where the continuity break was detected. This is the value the recovery arm uses to compute the rewind point. Having it structured means the scheduler can pattern-match on it precisely without string parsing, and tests can assert its exact value.

Importantly, ScanContinuity is not classified as transient (error.rs:48: is_transient() returns false for it). The reorg arm handles it directly in the scheduler loop — it never escalates to the pass-level retry logic (chapter 12), which is reserved for transport failures.

The recovery arm — verbatim semantics

When the scheduler receives a ScanContinuity{at} error from scan_chunks, it executes the recovery arm at scheduler.rs:207–263. The arm mirrors upstream's sync.rs:404–418 exactly:

// Mirror upstream rewind: err_height.saturating_sub(10)
// (sync.rs:409: `let rewind_height = err.at_height().saturating_sub(10)`)
let rewind_height = at.saturating_sub(10);

session
    .db_mut()
    .truncate_to_height(BlockHeight::from(rewind_height))
    .map_err(|e| SlipstreamError::Wallet(format!("truncate_to_height: {e}")))?;

// continue → causes suggest_scan_ranges to return the repair range
continue;

The rewind formula subtracts 10 blocks from the detected error height — conservative buffer to ensure the fork point is below the truncation point even if detection was slightly delayed. saturating_sub prevents underflow at genesis-adjacent heights.

truncate_to_height does three things atomically inside a single SQLite transaction:

  1. Removes all rows above rewind_height from the blocks, nullifier, and transaction tables.
  2. Rolls back the Sapling and Orchard shardtrees to the nearest checkpoint at or below rewind_height — this is the core of why rollback is fast.
  3. Updates the scan queue to reflect the new wallet state.

After truncation, continue sends the scheduler back to the top of its loop. suggest_scan_ranges now sees the truncated wallet and returns a repair range covering rewind_height+1 through the current tip. The engine fetches and scans this repair range against the current server treestate (fetched fresh at the start of the repair scan via retry_get_tree_state) — this is the "fresh server treestate re-anchoring" that makes the repair scan correct on the post-fork chain.

The checkpoint window and the sparse-mode subtlety

After truncation, select_truncation_height finds the nearest stored checkpoint at or below the requested rewind height. Upstream's shardtree prunes all but the 100 newest checkpoints after each insert_tree call — so only the most recent ~100 block heights survive as rewind anchors. If the requested rewind height falls in a gap (no checkpoint at exactly that height), the truncation snaps to the nearest surviving checkpoint below it.

This is the same post-prune state that upstream's own sync produces. As the darkside test truncate_rescan_oracle_is_clean (T6.5) demonstrates, the wallet state after a Slipstream truncate+rescan is byte-identical across all 26 tables to what upstream produces — the checkpoint window matches because Slipstream uses the same insert_tree / prune_excess_checkpoints machinery via scan_cached_blocks.

Sparse-mode note

In sparse-persistence mode (default on, chapter 7), checkpoints are written to the database inside the same per-chunk transaction. The checkpoint downgrade algorithm preserves only the newest 100 checkpoint IDs before they enter the in-memory tree, which is the same set prune_excess_checkpoints retains. The truncation behaviour is therefore identical between sparse and non-sparse modes. The T6.5 darkside oracle test verifies this directly with sparse=true.

Jittered backoff for load-balanced cluster tip-desync

The field story: rustSlipstreamSyncFailed(3375119) — a sync failure whose associated value decoded as the chain tip at the time of failure, not an error code. The leading hypothesis was that a load-balanced cluster (zec.rocks / eu.zec.rocks each terminates a single hostname on several backends) served a transiently stale tip from one backend, causing the wallet to see a reorg that wasn't real. Without backoff, the consecutive-reorg counter would burn through the five-recovery budget against the same momentarily-stale view in rapid succession, failing the restore for a transient condition.

The fix (B3, hardening1, scheduler.rs:47–49) adds deterministic backoff before re-suggesting after any reorg truncate:

pub(crate) fn reorg_backoff_ms(consecutive: u64) -> u64 {
    consecutive.saturating_mul(500).min(3_000)
}

The schedule: 500 ms, 1000 ms, 1500 ms, 2000 ms, 2500 ms for the five possible consecutive recoveries. Total worst-case added latency across the full budget: 7.5 seconds — negligible against a multi-minute restore. The cap at 3 s prevents runaway growth if the constant is ever changed.

Connection freshness on retry is structural, not added: the next loop iteration creates a new scan-side gRPC client (grpc::connect per range) and run_fetch spawns new per-worker connections (fetch.rs worker() connects per worker, per range). No channel survives into the retry, so the retry cannot be pinned to the same stale backend.

MAX_CONSECUTIVE_REORGS cap

If the server presents a genuinely adversarial chain or the database is corrupted, a naive recovery loop would cycle forever. The cap (scheduler.rs:28):

const MAX_CONSECUTIVE_REORGS: u64 = 5;

After five back-to-back ScanContinuity errors without a successful range completion in between, run_to_completion returns the last continuity error to the caller, setting the engine to the error state. The counter resets to zero on any successful range completion, so a single real reorg followed by successful recovery does not penalise future reorgs (scheduler.rs:284).

The compile-time bounds check (scheduler.rs:32–35) ensures the constant stays in the range [1, 10] — below 1, the first reorg is never recovered; above 10, infinite ping-pong becomes possible against a misbehaving server:

const _: () = {
    assert!(MAX_CONSECUTIVE_REORGS >= 1);
    assert!(MAX_CONSECUTIVE_REORGS <= 10);
};

Verified against darkside hardware

Two darkside tests verify the end-to-end reorg flow. Both require a local darkside lightwalletd instance (see CLAUDE.md) and are gated behind #[ignore].

Assertion: max(blocks.height) == 663202. The wallet recovered the correct tip.

Confirmed: sparse-mode truncate+rescan is byte-identical to upstream.

Known limitations

Honest gaps
  • The MAX_CONSECUTIVE_REORGS=5 cap is conservative and may surface as an error to the user in adversarial server scenarios. The app layer should present this as a recoverable error (restart the sync) rather than a permanent failure.
  • Tip-desync failure scenario (field failure 1) remains unconfirmed as the root cause of rustSlipstreamSyncFailed(3375119) — the Mac repro attempt produced 10/10 clean runs. The backoff mitigation addresses the plausible scenario regardless.
  • No tip-following between passes (single-shot runner, P8 gap): a reorg that occurs after a sync pass completes will only be detected at the start of the next pass when suggest_scan_ranges returns Verify-priority ranges. In-foreground tip-following is a known gap documented in chapter 19.
