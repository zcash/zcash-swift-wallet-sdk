9. Enhancement & Transparent

Estimated reading time: 14 minutes

1-minute summary

Enhancement is the process of fetching full transaction details — memos, confirmations, input/output metadata — for notes the wallet has already discovered during scan. It is architecturally separate from scan: scan identifies which transactions matter; enhancement fetches everything about them. This chapter covers the three-round TransactionDataRequests loop, the concurrent txid-fetch pipeline, the per-pass dedupe guard, the three interleave layers in the scheduler, transparent UTXO refresh ordering, and the documented gap in address-based enhancement.

The three-round TransactionDataRequests loop

Enhancement entry is run_enhancement (enhance.rs:83–174). It does not decide which transactions to enhance — that decision belongs to the upstream library (D2). It calls wallet.transaction_data_requests(), which returns a list of TransactionDataRequest items describing what the library needs. The engine fetches and stores the requested data, then calls transaction_data_requests() again. The loop runs up to three rounds:

// enhance.rs:83–108 (simplified)
for round in 0..3 {
    let requests = wallet.transaction_data_requests()?;
    if requests.is_empty() { break; }

    process_txid_requests(&requests).await?;
    process_address_requests(&requests, &mut skipped_keys).await?;
}

Three rounds covers the real cascading case: round 1 fetches a transaction that introduces a new note; round 2 fetches any follow-up requests the library generates after seeing that transaction (e.g., checking its transparent inputs); round 3 is a safety pass for anything that cascaded from round 2. In practice most runs need only one round; the three-round cap prevents unbounded looping on pathological inputs.

Concurrent txid fetches

Within each round, txid requests (TransactionDataRequest::GetStatus and ::Enhancement) are dispatched concurrently via FuturesUnordered (enhance.rs:125–160). Up to FETCH_CONCURRENCY=8 in-flight gRPC calls run simultaneously. Results are processed as they complete (not in submission order), so a slow server response on one txid does not block other fetches.

The two txid request arms differ in what they store:

Request typegRPC callResult
GetStatusGetTransactionSets transaction status only (mined height or pending); no note decryption.
EnhancementGetTransactionFull decrypt_and_store_transaction: memos, nullifiers, output metadata.

Both arms use the same GetTransaction RPC. The distinction is in how the result is applied: GetStatus extracts only the mining height (>0 → Some(height); ==0 → None, indicating pending), while Enhancement passes the full transaction bytes to the upstream decrypt_and_store_transaction. This respects the upstream write-path contract; Slipstream never writes transaction rows directly.

Per-pass address request dedupe

Address-based requests (TransactionDataRequest::TransactionsInvolvingAddress) trigger a GetTaddressTxids streaming RPC that fetches all transactions involving a transparent address in a block range. These requests can be generated repeatedly for the same address across multiple enhancement interleave calls within one sync. Without a dedupe guard, the engine would issue duplicate RPCs on every interleave call — wasting bandwidth and causing duplicate row inserts.

The guard is a HashSet<String> called skipped_keys (enhance.rs:262–272), scoped to one run_enhancement call. The key is the transparent address string. Before issuing a GetTaddressTxids RPC, the engine checks whether the address is already in skipped_keys; if so, the request is skipped entirely. After processing, the address is inserted into skipped_keys.

T4.6 fix context

The dedupe guard was added in the T4.6 session (STATE.md) after observing address requests re-queued on every interleave call for wallets with high transparent activity. The fix reduced unnecessary RPC traffic from O(interleave_calls × addresses) to O(addresses) per sync, while preserving the semantic that every address is fetched at least once per enhancement call.

Three skip guards on address requests

Before any address RPC, the engine applies three guards in order (enhance.rs:265–285):

  1. Missing blockRangeEnd (now clamped, T8.5): an open-ended request clamps to chain_height+1 via effective_range_end and is serviced as a closed [start, tip] range rather than skipped — see below. The request is only skipped if there is genuinely no scanned chain tip yet (defensive; cannot occur after preflight).
  2. Set requestAt: requests carrying a decorrelated-fetch anchor are skipped (privacy-decorrelated scheduling not implemented) — matching the old SDK.
  3. Status already Unspent: if the UTXO is already marked as unspent (fully processed), the request is redundant and skipped.

The open-ended address range: clamped to the tip (T8.5)

When blockRangeEnd is absent from a TransactionsInvolvingAddress request, the request means "unbounded above." The completest answer lightwalletd can give right now is through the chain tip, so the engine clamps the range to chain_height+1 via effective_range_end and services it as an ordinary closed [start, tip] request — the same byte-budget and deadline mechanisms bound it as every other call. After success, notify_address_checked(tip) records the watermark, so any activity above the tip is re-issued on the next pass with no coverage gap.

Completeness — closed (T8.5)

Open-ended ranges are no longer skipped: they clamp and service against the current tip. The only residual skips are the requestAt and Unspent guards, which fire for ephemeral ZIP-320 checks — and those upstream producers also set requestAt + Unspent, so they skip here for exactly the same reason the old SDK skips them. Privacy: the clamped request sends the same address strings as any other closed-range query. See chapter 15 for the privacy model, and chapter 19 for the roadmap context.

The three interleave layers

Enhancement does not run only at the end of sync. It is woven through the scan pipeline at three granularities to provide timely balance updates:

Layer 1: every K chunks (inside scan)

should_interleave_enhancement(chunks_done, every=3) (scan.rs:71–73) returns true when chunks_done > 0 && chunks_done % every == 0. When true, scan_chunks calls run_enhancement before fetching the next chunk. The enhancement elapsed time is tracked separately and excluded from the scan_s metric reported in per-chunk logs — so benchmarks reflect net scan time and are not inflated by enhancement latency.

Layer 2: per range (in scheduler)

After each scan range returns, the scheduler calls run_enhancement (scheduler.rs:325–351). This ensures that notes discovered during the range are enhanced before the wallet UI reflects the completed range — the ranges_completed increment happens after the per-range enhancement call, so a snapshot taken at ranges_completed == N already includes the enhancement work for range N.

Layer 3: final backstop (end of pass)

After all ranges in a pass have been scanned, the scheduler calls run_enhancement once more as a backstop. This catches any requests that: (a) were generated after the last range's layer-2 call, or (b) required a cascade that didn't resolve until all ranges were complete. The backstop is also the only enhancement call for passes where the layer-1 interleave never fired (e.g., a pass that covers only one short range with two chunks).

Transparent UTXO refresh ordering

Transparent UTXO refresh runs before any shielded scanning. This ordering is an upstream contract, documented in a comment at transparent.rs:53–55:

// transparent.rs:53–55 — upstream-mirroring contract
// We do this before we perform any shielded scanning, because the note
// commitment tree state at any given block height requires that the
// transparent balance be up-to-date.

The refresh call (refresh_utxos, transparent.rs:63–155) iterates over all accounts in the wallet, queries the wallet's own transparent receivers (via get_transparent_receivers), then calls get_address_utxos on the lightwalletd service for each receiver, and stores the results via put_received_transparent_utxo. The return value maps each UtxoRef to () — the engine does not inspect UTXO content; it delegates all semantic decisions to the upstream database layer.

Transparent UTXOs are not part of the commitment tree; their presence does not affect the Sapling or Orchard tree state. The ordering requirement exists because subsequent shielded scanning may spend transparent inputs: the upstream scanning library needs the transparent balance to be consistent before it can correctly compute the note-spending context for mixed transparent+shielded transactions.

EnhanceStats: what is counted

EnhanceStats (enhance.rs:41–55) accumulates four counters across one run_enhancement call:

FieldMeaning
requestsTotal TransactionDataRequest items processed (all types, all rounds).
txs_storedFull transactions stored via decrypt_and_store_transaction.
statuses_setTransaction statuses updated (GetStatus arm results).
skippedAddress requests skipped by any of the three guard rules.

At the end of run_enhancement, txs_stored + statuses_set is added to the global Progress.enhanced_txs counter (enhance.rs:168–172). This is the number exposed to Swift via snapshot().enhanced_txs.

Why enhanced_txs is monotonic, not per-pass

A caller monitoring the wallet may want to show "3 transactions synced" in a notification. If this counter reset on each pass, a caller that read the snapshot mid-sync would see an apparently smaller number after a reorg recovery. Making it a monotonic-delta (per-handle) counter ensures that callers only ever see the number go up, even across reorg recoveries and multiple passes.

Known limitations

Honest gaps
  • Open-ended address range now clamped (T8.5): Requests without a blockRangeEnd are clamped to chain_height+1 and serviced as a closed range, then re-issued for any activity above the tip on the next pass. The residual requestAt/Unspent skips cover only ephemeral ZIP-320 checks — matching the old SDK. See chapter 15 for the privacy implications of address queries.
  • Three-round cap: Enhancement loops at most three rounds per invocation. A pathological wallet state that requires more than three cascade levels per range would not be fully enhanced in one interleave call. In practice, one or two rounds is the observed maximum; three is a conservatively generous bound.
  • Mempool surfacing vs. enhancement detail: 0-conf wallet-relevant transactions — including the wallet's own outgoing spends, which appear in the mempool — are now surfaced via the T8.2 mempool stream (between follow passes). The transaction_data_requests enhance path itself still fills full transaction detail only for mined txs, because the upstream library drives those requests off confirmed state.
  • Address stream dedupe is per-invocation: the skipped_keys HashSet is created fresh in each run_enhancement call. Across the three interleave layers in a single pass, the same address may be queried up to three times (once per layer). Within one call, it is queried at most once.
