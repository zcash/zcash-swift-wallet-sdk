ZcashLightClientKit · Slipstream · Chapter 4

Integration Guide

Part I — Overview  ·  estimated reading time: 14 minutes

1-minute summary

Slipstream has four integration layers: an engine-generic Rust core (slipstream-core), a C FFI surface (six zcashlc_slipstream_* functions), a Swift actor seam (SlipstreamEngine + SlipstreamSynchronizer), and app-level configuration (Zodl's server selection and retry logic). This chapter is a reference for integrators — including the Android SDK team, who would dock against the Rust core directly, and third-party wallet teams reusing the engine. Every configuration field is documented with its default, validation rule, and purpose.

Layer overview

Layer 1 — slipstream-core (engine-generic Rust)

slipstream-core is a platform-neutral Rust crate at slipstream/core/. It depends only on the same zcash_client_sqlite / zcash_client_backend versions already in the workspace. It has no iOS SDK, Android NDK, or Swift dependencies.

An Android SDK team or any non-iOS platform would integrate at this layer, using the crate's public async function:

// slipstream/core/src/engine.rs — the public entry point
pub async fn sync_once(
    config: &EngineConfig,
    ufvk: Option<(&str, u64)>,  // (UFVK string, birthday height), or None for keyless
    progress: Option<Arc<Progress>>,
) -> Result<SyncOutcome, SlipstreamError>

The caller needs to provide a tokio runtime, open an EngineConfig, and drive the retry/lifecycle loop. The iOS Swift layer does this through the six C FFI functions — Android would do equivalent work in Kotlin/JNI or via a uniffi binding over the same core (Decision P7, decoupled from this prototype — iOS is the reference implementation, per the user's 2026-06-11 decision).

Layer 2 — C FFI surface

The six zcashlc_slipstream_* functions in rust/src/lib.rs are the integration contract for the C/Swift boundary. They follow the exact same handle pattern as the existing TorRuntime FFI in the same file.

Lifecycle

// rust/src/lib.rs — open allocates; free deallocates.
// open → start (→ stop → start)* → free
//          ↑                 ↑
//      snapshot/drain may be called at any point between open and free
FunctionParametersReturnsContract
zcashlc_slipstream_open db_data (path bytes), server_host, server_port, use_tls, network_id (1=main) *mut SlipstreamHandle or null on error Allocates tokio runtime (4 workers), progress atomics, event ring. Installs panic tracing hook (B1). Must call free on the returned pointer eventually.
zcashlc_slipstream_start handle, ufvk (nullable), ufvk_len, birthday_height bool success Cancels any in-flight task; spawns new supervised sync task. SyncStarted (tag=1) emitted exactly once, before any pass-level retry. UFVK=null/len=0 = keyless update (account must already be imported). Can be called again after stop to restart.
zcashlc_slipstream_stop handle bool (always true) Aborts in-flight task; sets state to Idle. Non-blocking — returns immediately. Poll snapshot to confirm state transition.
zcashlc_slipstream_snapshot handle (const) FfiSlipstreamSnapshot (by value) Non-blocking read of all progress atomics + state. Zero-filled on null handle. Never blocks the caller.
zcashlc_slipstream_drain_events handle, buf (caller-allocated array), buf_len usize count drained Atomically drains up to buf_len events into caller's buffer. Drained events removed from ring. Ring capacity is 64; overflow drops oldest.
zcashlc_slipstream_free handle (nullable) void Aborts in-flight task, drops tokio runtime. Null-safe. Pointer must not be used after this call.

Poll contract (D8)

The Swift layer polls every 2 seconds. On each tick it calls snapshot (non-blocking, returns by value) and drain_events (atomically drains the ring). There are no callbacks, no cross-FFI notifications, no thread-pinning requirements on the caller side. The runtime's threads are entirely internal to the handle.

State values in snapshot.state: 0 = Idle, 1 = Syncing, 2 = Error, 3 = Done. The transition to Done emits a SyncDone (tag=3) event before any subsequent snapshot would read Done.

Pass-level retries: if a transient transport error occurs during a sync pass, the Rust runner retries up to 2 more times (3 total), sleeping 5s after the first failure and 15s after subsequent ones (PASS_RETRY_MAX=2, in rust/src/lib.rs). State stays Syncing throughout. SyncStarted is emitted once at the beginning, not at each retry. Progress counters (ratio fields) reset at each retry's begin_pass() — the denominator is recomputed from remaining ranges, which is correct. Delta counters (enhanced_txs, ranges_completed) are untouched.

Layer 3 — Swift seam

SlipstreamSynchronizer

SlipstreamSynchronizer implements the same Synchronizer protocol as SDKSynchronizer. The app (Zodl) selects between them via a feature flag; from the app's perspective they are interchangeable.

The delegation split is:

Member categoryDelegated toCount
Sync members (start/stop/state/events/rescan/rewind/wipe/switchTo/latestHeight)SlipstreamEngine + lightWalletService~9

All of these delegates come from the existing DIContainer (the same dependency-injection root as SDKSynchronizer). No new singletons or services are introduced. The two synchronizers can even share the same data.db because both read from and write to it through the same upstream zcash_client_sqlite layer.

SlipstreamEngine

SlipstreamEngine is a Swift actor that serialises all calls to the C FFI functions. It mirrors the TorClient pattern (see Tor/TorClient.swift). The actor's lifecycle:

  • open(network:) — calls zcashlc_slipstream_open. Idempotent (no-op if already open).
  • start(ufvk:birthday:) — calls zcashlc_slipstream_start.
  • stop() — calls zcashlc_slipstream_stop.
  • snapshot() — calls zcashlc_slipstream_snapshot, wraps result in SlipstreamSnapshot.
  • drainEvents() — calls zcashlc_slipstream_drain_events into a fixed-size buffer.
  • close() / deinit — calls zcashlc_slipstream_free.
  • reopen(server:network:) — for switchTo: closes old handle, opens new one with updated endpoint.

Polling and progress mapping

A 2-second polling Task in SlipstreamSynchronizer calls engine.snapshot() and engine.drainEvents() every tick. The snapshot is mapped to a SynchronizerState using the following rules (from SlipstreamSynchronizer+PureHelpers.swift):

  • state=0 (Idle): .unprepared or .prepared depending on whether open() has been called.
  • state=1 (Syncing): .syncing(progress, spendable) where progress = scannedBlocks / passTotalBlocks (clamped 0–1; denominator 0 → 1.0 per upstream behaviour). spendable = spendableHint == 1.
  • state=2 (Error): .stopped.
  • state=3 (Done): .synced (emitted immediately; wallet summary fetched after, does not delay the .synced emission).

Stall watchdog (B4)

A 120-second watchdog in SlipstreamSynchronizer+StallWatchdog.swift fires a Logger.error if the engine stays in state=1 (Syncing) with zero counter movement. This is the Swift-side companion to the Rust-side B1 panic supervisor. The watchdog only logs — it never restarts. The threshold (120s) is chosen to be comfortably above the worst observed legitimate counter gap (36s on iPad A10).

Layer 4 — App-specific (Zodl)

Zodl adds two integration touches specific to its architecture that other integrators would not necessarily replicate:

  1. Server race-before-start: await autoServerSelection.refreshIfEnabled() is called before sdkSynchronizer.start() in both initializeSDK and retryStart (T6.8-L1, RootInitialization.swift in the Zodl repo). This ensures the best server is selected before the pass begins, eliminating the ~50s iPad restart cost of an AutoServerSelection switch mid-sync.
  2. retryStart: Zodl's foreground-resume path calls retryStart, which calls the SDK's start() again. The engine-level pass-level retry (3 total attempts for transient errors) is distinct from this app-level restart.
For Android or other platform integrators

An Android integration would dock at Layer 1 (slipstream-core crate). The Rust crate is platform-neutral. The approach mirrors how libzcashlc slots into zcash-android-sdk's backend-lib: compile slipstream-core alongside the existing Rust backend, expose it via JNI or uniffi, and drive the sync_once loop from a Kotlin coroutine. The iOS Swift seam in this repo is the reference implementation for that work. Uniffi bindings are the preferred shape (lower JNI boilerplate); decision is deferred to P7.

EngineConfig reference

All engine behaviour is controlled through EngineConfig in slipstream/core/src/config.rs. Fields are public; defaults are set by EngineConfig::new.

FieldTypeDefaultValidationPurpose
network Network Caller-supplied — MainNetwork or TestNetwork. Passed to all upstream API calls.
wallet_db_path PathBuf Caller-supplied — Path to the existing data.db managed by zcash_client_sqlite.
endpoint Endpoint Caller-supplied host non-empty lightwalletd server. Endpoint { host, port, tls } — TLS flag selects https vs http scheme.
fetch_streams usize 4 ≥ 1 Number of concurrent GetBlockRange sub-streams. Higher values improve throughput on fast networks but increase server-side load. zec.rocks tolerates K=4 well.
chunk_blocks u32 10,000 ≥ 100 Target blocks per in-memory chunk / per scan_cached_blocks call. One SQLite transaction per chunk. Larger values amortise transaction overhead; smaller values reduce peak memory and improve progress granularity.
memory_budget_bytes usize 256 MiB ≥ 16 MiB Maximum in-flight downloaded block data in the ChunkQueue. Controls the maximum number of chunks that can be prefetched ahead of the scanner. Wire data; decoded blocks occupy more memory.
chunk_split_bytes usize 8 MiB ≥ 1 MiB Byte budget per emitted fetch sub-chunk (T6.8-S). Normal-era 10k-block chunks (~1–6 MB wire) stay single sub-chunks. Sandblasting era chunks (~100s of MB) split into many small sub-chunks automatically — density-adaptive, no hardcoded heights. The 120s progress deadline bounds ONE sub-chunk, not the whole chunk.
scan_batch_target_ms Option<u64> None None or ≥ 500 ms When Some(ms), splits each fetch-chunk into time-targeted scan sub-batches (~ms each) via the adaptive controller (T5.2). Costs one full put_blocks commit per sub-batch (~1.5–2s on A10). None = one scan_cached_blocks call per chunk (default; fastest on all hardware).
enhance_every_chunks u32 3 ≥ 1 Run an interleaved (non-fatal) enhancement pass every N completed chunks within a range scan, so found transactions surface progressively (T6.1). The per-range and final post-loop enhancement runs are unaffected backstops.
sparse_persistence bool true — Use the sparse in-memory commitment-tree path (P6). Default ON since T6.6 — oracle-clean (hermetic + darkside + mainnet IDENTICAL; reorg + truncate compatibility verified). Kill switch: set false to revert to the upstream path if a regression is found. The 5× Mac scan speedup comes from this flag.
CLI equivalents (for local benchmarking)

All EngineConfig fields are exposed as slipstream-cli sync flags: --streams (fetch_streams), --chunk-blocks, --memory-budget (bytes), --chunk-split-bytes, --scan-batch-ms (scan_batch_target_ms, None by default), --enhance-every (enhance_every_chunks), --sparse/--sparse false (sparse_persistence).

ENGINE_BUILD freshness-tag discipline

Every engine change that warrants a framework rebuild bumps the ENGINE_BUILD constant in slipstream/core/src/engine.rs:

// slipstream/core/src/engine.rs:25
pub const ENGINE_BUILD: &str = "2026-06-13.walltime";

This string is logged at every sync pass start, in the stage-split line, and at runner failure. It is the definitive freshness check for device logs: if the tag in a device log does not match the HEAD value, the device is running a stale XCFramework.

To probe a built slice: strings <slice>/libzcashlc.framework/libzcashlc | grep <tag>. If the expected tag is absent, the slice needs a rebuild via ./Scripts/rebuild-local-ffi.sh.

When bumping: update the string in engine.rs, then run ./Scripts/init-local-ffi.sh (full 3-slice rebuild) or the relevant rebuild-local-ffi.sh <target> for incremental development.

What an Android integration would look like

The slipstream-core crate is intentionally free of iOS/Swift platform dependencies. An Android integration follows the same layering as the current libzcashlc slot in zcash-android-sdk:

  1. Add slipstream-core as a crate dependency in the Android backend's Rust workspace.
  2. Expose a sync_once wrapper via JNI or a uniffi binding definition (uniffi preferred — lower boilerplate; JNI acceptable as a fallback).
  3. In Kotlin, drive the lifecycle loop: open a config, call the sync function inside a coroutine, poll a shared-state object for progress, surface events.
  4. Handle restart/lifecycle from the Kotlin side — the Rust function is synchronous from the Android coroutine's perspective (it is an async future, but the JNI or uniffi bridge blocks the calling coroutine until the pass completes or fails).

The iOS Swift seam in this repo is the reference implementation for that work. Every design choice — poll-based progress, separate event ring, pass-level retry, panic supervisor — was made with platform-generic constraints in mind.

Known limitations

Integration gaps
  • Mempool (0-conf) detection (DONE, T8.2): between follow passes the engine holds a get_mempool_stream, dedupes by txid, and stores wallet-relevant unconfirmed transactions 0-conf via decrypt_and_store_transaction(mined_height=None). Non-fatal — on a failure cap it disables the mempool session and keeps tip-polling.
  • In-foreground tip-following (DONE, T8.1): after each pass the engine enters a jittered 10–30 s probe loop and launches a keyless catch-up pass whenever the server tip advances; integrators no longer have to call start() again on every new block. The loop is cancelled by the engine's AbortHandle on stop/free.
  • Tor wired (DONE, T-Tor): when the host enables Tor, the engine bootstraps its own arti client and routes wallet-identifying gRPC calls over isolated Tor circuits while the bulk download stays direct (mirrors the old SDK's per-call policy). See chapter 15.
  • Transparent enhancement — open-ended requests now serviced (T8.5): TransactionsInvolvingAddress requests with no blockRangeEnd now clamp to chain_height+1 and are serviced as a closed [start, tip] range (with notify_address_checked(tip)), no longer skipped. The residual ephemeral ZIP-320 requests still skip via the requestAt/Unspent guards — exactly as the old SDK does.
  • data.db at-rest protection is app-level: Slipstream does not add any encryption layer. Integrators are responsible for OS-level file protection (keychain, secure enclave, NSFileProtectionComplete, etc.).
  • A10-class spam-era memory untuned: the sandblasting era (mainnet ~1.70M–2.00M) requires ~1.3–1.84 GB RSS on Mac; on A10-class devices (2 GB RAM, jetsam) this range is not yet safe. The engine is traversable from a Mac/iPhone-16-Pro perspective; device-class memory budgeting is an open task (Blockers, STATE.md).
  • L2 row batching seam-blocked: bulk SQL insert for the blocks and related tables would be the next significant scan speedup, but is blocked at the zcash_client_sqlite public API boundary — requires upstream collaboration or a vendored fork (not taken).
  • L4a decrypt kernel parked: a custom ECDH trial-decryption kernel is the lever to reach Zkool-class performance on modern hardware but requires a new oracle harness. Deferred.
