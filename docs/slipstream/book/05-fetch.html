5. Fetch Pipeline

Estimated reading time: 14 minutes

1-minute summary

The fetch pipeline downloads compact blocks in parallel using K=4 workers, each claiming consecutive plan chunks from an atomic counter. Each plan chunk is split on-the-fly into byte-budgeted sub-chunks (≤8 MiB wire bytes each) by a ChunkSplitter. Sub-chunks are tagged with a (plan_index, sub_index, is_last) ordering key and reassembled in strict order by a reorder stage that feeds the ChunkQueue — a Tokio semaphore providing byte-budget backpressure between fetch and scan. An AheadGate prevents non-floor workers from parking hundreds of megabytes of spam-era data in the reorder buffer simultaneously. Transport errors trigger a resume-from-height retry: the cursor advances only past successfully emitted sub-chunks, so double-scan is structurally impossible. The sandblasting era is handled here — see chapter 11 for the full denial-of-service story.

The claim-based worker model

The range for a given scan pass is divided into plan chunks of chunk_blocks blocks each (default 10,000). A shared Arc<AtomicU64> counter named next acts as a work queue: each worker calls fetch_add(1, Relaxed) to claim the next unclaimed plan index. This avoids any scheduler or message-passing overhead — workers claim work as fast as they finish, naturally balancing load.

// fetch.rs:416 — each worker's main loop
let index = next.fetch_add(1, Ordering::Relaxed);
if index >= plan.chunk_count() {
    return Ok(()); // no more work
}
let (s, e) = plan.chunk_range(index);

Each plan chunk owns an independent gRPC GetBlockRange stream (fetch.rs:379–403). Workers reconnect on retry (a fresh grpc::connect call), so a poisoned channel from a prior error is abandoned rather than reused.

Plan chunks vs sub-chunks: the ChunkSplitter

A plan chunk is a 10,000-block unit determined by the fetch plan. A sub-chunk is the unit actually sent to the reorder stage and ultimately to the ChunkQueue. In normal-era operation (blocks outside the 2022 spam band), one plan chunk produces exactly one sub-chunk — behaviour is identical to a pre-split engine. In the sandblasting era, a plan chunk may produce up to 131 sub-chunks (observed in the field; see chapter 11).

The ChunkSplitter (fetch.rs:137–169) is a streaming accumulator. It receives blocks one at a time from the gRPC stream and yields a completed sub-chunk whenever adding the next block would push the accumulated wire size past split_bytes (default 8 MiB; configurable via EngineConfig::chunk_split_bytes):

// fetch.rs:150–163 — the split decision
pub(crate) fn push(&mut self, block: CompactBlock) -> Option<(Vec, usize)> {
    let block_bytes = Message::encoded_len(&block);
    let completed = if !self.acc.is_empty() && self.acc_bytes + block_bytes > self.split_bytes
    {
        let blocks = std::mem::take(&mut self.acc);
        let bytes = std::mem::replace(&mut self.acc_bytes, 0);
        Some((blocks, bytes))
    } else { None };
    self.acc.push(block);
    self.acc_bytes += block_bytes;
    completed
}

Two invariants are guaranteed by construction: the splitter never yields an empty sub-chunk, and a single block larger than the budget forms its own sub-chunk rather than causing an infinite loop (the condition requires the accumulator to be non-empty before splitting).

The (plan_index, sub_index, is_last) ordering key

The reorder stage must release sub-chunks in strict order across potentially out-of-order workers. The key is a triple rather than a single integer:

FieldSemantics
plan_indexIndex of the plan chunk (0-based, from the atomic counter).
sub_indexIndex of this sub-chunk within its plan chunk. Dense from 0; survives retries — a resumed attempt continues the sequence from where it left off, never repeating an index.
is_lastMarks the final sub-chunk of a plan chunk. The reorder stage advances to plan chunk N+1 only after it has seen N's is_last.

The sub_index surviving retries is load-bearing: if a worker fails after emitting 8 sub-chunks, reconnects, and resumes from the next height, sub-chunk 8 is tagged with sub_index=8, not 0. The reorder stage therefore sees a dense, gapless sequence and can validate it without special-casing retries.

The reorder stage and ChunkQueue

After all workers have pushed their sub-chunks into the channel (mpsc::channel capacity = number of workers), the release_ordered function (fetch.rs:487–541) drains them in strict (plan_index, sub_index) order using a BTreeMap<(u64, u64), SubChunk> as a pending buffer. Continuity is verified by the Continuity checker (from verify.rs) across every sub-chunk seam, including across sub-chunk boundaries within the same plan chunk and across plan-chunk boundaries.

Each released sub-chunk is sent to the ChunkQueueSender (chunk.rs:76–94), which acquires a Tokio semaphore permit proportional to the chunk's estimated wire bytes before enqueuing. The semaphore's budget is EngineConfig::memory_budget_bytes (default 256 MiB). The scanner holds the permit until the chunk's last sub-batch is committed (scan.rs:349: drop(permit) after the final sub-batch of the chunk), so the budget covers bytes that are queued and bytes that are actively being processed:

Backpressure semantics

The byte budget covers both enqueued bytes and in-flight bytes (the scanner holds the permit until the chunk is fully committed). An oversized chunk that exceeds the entire budget is clamped to the full budget rather than deadlocking (chunk.rs:81: min(self.budget_bytes)). This means memory is bounded by the budget plus one scan-in-progress chunk — never unbounded.

AheadGate: bounding the reorder buffer

Without admission control, K−1 workers could each be streaming a spam-era plan chunk simultaneously (each several hundred MB to over a GB), parking all of it in the reorder buffer while the floor worker (plan 0) is being drained. On four workers this represents up to 3 GB in memory — well past device jetsam limits on A10-class iPhones.

The AheadGate (fetch.rs:193–229) solves this with a Tokio semaphore of capacity 8 × split_bytes (= 64 MiB by default). The floor plan chunk — the one currently being released by the reorder stage — streams unthrottled and is exempt from the budget. All other ("ahead") workers must acquire byte-unit permits before emitting a sub-chunk; if the budget is spent, they pause until the reorder stage drains buffered sub-chunks and drops their permits.

Deadlock analysis

The AheadGate is deadlock-free by design: the floor never waits on the budget; a blocked worker re-checks whether it has become the floor every 100 ms (AHEAD_POLL); and the budget is freed exactly when the reorder stage drains sub-chunks, which happens immediately after the scanner consumes from the ChunkQueue. The single-semaphore design avoids any cross-lock ordering.

In normal-era operation (one sub-chunk per plan chunk, each ~1–6 MB), the 64 MiB budget admits at least 8 sub-chunks in parallel — no throttling occurs and the AheadGate adds no latency.

Deadlines: per-sub-chunk, not per-plan-chunk

The chunk_timeout (default 120 seconds) now bounds the accumulation of one sub-chunk, not the entire plan chunk. The deadline is measured from the last time a sub-chunk was emitted; it resets on every successful emission (fetch.rs:366: last_progress = tokio::time::Instant::now()).

This is the key fix for the sandblasting era (chapter 11): a plan chunk that contains 2.5 million outputs across 10,000 blocks takes far longer than 120 seconds to download, but it emits sub-chunks continuously — each sub-chunk resets the deadline. Only a genuinely stalled stream (no messages for 30 seconds, via grpc::STREAM_IDLE_TIMEOUT) times out.

An additional per-message idle timeout inside next_with_idle_timeout (in grpc.rs) ensures that a server that accepts the request but silently stops sending is detected within 30 seconds rather than waiting for the per-sub-chunk progress deadline.

Resume-from-height retry: double-scan impossibility

When a plan chunk's download fails partway through, the PlanChunkCursor tracks the last height successfully emitted. On retry, the worker opens a new gRPC stream starting at resume_from (the height after the last emitted sub-chunk's last block).

The cursor only advances on a successful send into the mpsc channel (fetch.rs:289–293). A failed send does not advance resume_from. Already-emitted sub-chunks are never re-sent to the reorder stage — their heights have already been released to the ChunkQueue and consumed by the scanner. The reorder stage also verifies continuity via Continuity.verify_blocks() at every sub-chunk seam; a duplicate height would produce a Discontinuity error. Double-scan is therefore structurally impossible: no code path can cause a height to enter the ChunkQueue twice.

The retry loop: zero-progress counting

Each worker tracks how many consecutive zero-progress attempts it has made per plan chunk. An attempt is "zero-progress" if no sub-chunk was emitted. If a transport error occurs mid-stream after emitting sub-chunks, the attempt resets the counter (since emitted_this_attempt = true) and the worker gets a fresh budget of retries_per_chunk (default 3) zero-progress retries. This means a very large spam-era chunk that loses its connection repeatedly can still complete as long as it makes forward progress on each attempt; only a permanently stalled server exhausts the budget.

Backoff between attempts is exponential with a cap: 250ms × 2^attempt, bounded to prevent overflow (fetch.rs:459–463). The worker reconnects on every retry (new grpc::connect call) so stale channels are never reused.

Known limitations

Honest gaps
  • No server-authenticated block hashes at download time: the reorder stage verifies prev-hash continuity (sequential linkage), but the cryptographic commitment to the server's data is only verified by the scan kernel (scan_cached_blocks). A compromised lightwalletd can serve internally-consistent but fabricated blocks; the trust model is documented in chapter 14.
  • Backpressure latency on spam-era transitions: when the first spam-era plan chunk arrives, the AheadGate may briefly throttle workers 1–3 while worker 0 drains. This is expected and correct; it manifests as a momentary slowdown at height ~1,700,000 during a full wallet restore.
