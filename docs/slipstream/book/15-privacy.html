15. Privacy Analysis

1-minute summary · reading time ≈ 10 min

This chapter documents, with precision grounded in the source code, exactly what the lightwalletd server learns about a wallet when Slipstream syncs. The most significant facts: the wallet's transparent addresses are sent to the server during enhancement, and its transaction IDs of interest are revealed via GetTransaction. When Tor is enabled, those wallet-identifying calls are routed over isolated Tor circuits while the bulk compact-block download stays direct — mirroring the old SDK's per-call Tor policy exactly (§15.3). These leakages are protocol-inherent and shared with the upstream SDK; this chapter states plainly what the server learns, and what Tor does and does not hide.

This chapter's honesty register

Every claim in the "what the server learns" table is verified against the source code at commit e31bd005 (Tor integration). Claims that cannot be verified from the code are marked UNVERIFIED. No claim is made about anonymity or privacy properties not supported by the code.

15.2 What the server can never learn from Slipstream

The following information is processed entirely on-device and is never transmitted to the server:

  • Spending keys and the UFVK itself. The UFVK is decoded in wallet_session.rs at ensure_account (line 75) and imported into the local SQLite database. The UFVK string is consumed within the process — it is never passed to any gRPC function. The server receives no key material of any kind.
  • Which shielded outputs decrypted to notes belonging to this wallet. Trial decryption happens inside scan_cached_blocks using the viewing key that was imported locally. The server provides compact blocks (ciphertext only); the engine determines locally which ciphertexts decrypt successfully. The server cannot observe which outputs were successfully decrypted.
  • Shielded balances. Balances are computed by the upstream wallet brain from the locally-held note records. No balance query goes to the server.
  • Memos. Memo fields in Sapling and Orchard outputs are decrypted locally during note decryption. They are never transmitted.
  • The wallet's spend history or internal note positions. Nullifiers and note commitment tree positions are computed and stored locally.

15.3 Tor: engine-owned circuits, mirroring the old SDK

As of the Tor integration (ENGINE_BUILD 2026-06-17.tor), Slipstream routes its sync over Tor when the host wallet enables it — using the same per-call policy the old SDK established (that policy was designed and reviewed by the engineer who drove Tor into the SDK). The rule splits by call type:

CallTransport when Tor is ONWhy
Bulk block fetch (GetBlockRange, 4 streams)Direct — never TorPublic range data, too high-volume for Tor; mirrors the old SDK's blockStream(.direct), and keeps full sync speed.
GetTreeState, GetLatestBlockIsolated Tor circuit (.uniqueTor)Wallet-correlated metadata; a fresh circuit per connection.
GetLightdInfo (server validation)Default Tor circuit (.defaultTor)Mirror of the old SDK.
GetTransaction (enhancement)Tor circuit grouped by txid (.txIdGroup)Hides which txids this wallet fetches from the syncing IP.
Transparent GetTaddressTxids / GetAddressUtxosIsolated Tor circuitHides the wallet's transparent addresses from the syncing IP.
Transaction submitIsolated Tor circuitHides which IP broadcast a transaction.

What this hides — and what it does not. With Tor on, the lightwalletd operator still observes the wallet's real IP and approximate birthday range on the direct bulk download — exactly as the old SDK does, by deliberate design (the bulk stream is public block data, and routing hundreds of MB over Tor would defeat the engine's speed). What Tor does hide is the linkage between that IP and the wallet's specific identifying operations: the transaction IDs it fetches, the transparent addresses it queries, the treestate heights, and its transaction broadcasts each travel over a separate isolated Tor circuit (a distinct exit IP), so the operator cannot tie them to the syncing IP. This is privacy parity with the old SDK — neither weaker nor stronger.

Engine-owned, resilient, never-falls-back

The engine bootstraps its own arti Tor client on its own async runtime (zcash_client_backend::tor::Client::create binds to the ambient runtime — no block_on, no second runtime), from a dedicated state directory separate from the old SDK's TorClient dir (arti holds a per-directory state lock). Bootstrapping is resilient: a transient failure surfaces as Disconnected and retries with capped backoff indefinitely — it never silently falls back to a direct connection, because a Tor-requesting user must not be de-anonymised by a network blip. Enabling Tor therefore costs a one-time circuit bootstrap (a few seconds, overlapping the direct bulk fetch) but not the old SDK's whole-engine slowdown: the wallet syncs at full speed with Tor on.

Tor off is byte-for-byte the previous behaviour — the connector's direct path is the literal grpc::connect call, unchanged, and the golden oracle confirms an identical data.db.

Residual IP exposure (unchanged from the old SDK)

Because the bulk download is direct, a user who additionally wants to hide the fact and IP of syncing (not just unlink their specific operations) must still route the connection through an external VPN or system-level Tor — the engine's bulk path provides no IP protection, by the same design choice as the old SDK.

15.4 Data at rest

data.db is a standard SQLite file written to the app's document directory. At the engine level, the database is not encrypted — the engine calls pragma_update_and_check(None, "journal_mode", "wal") and pragma_update(None, "synchronous", "NORMAL") but does not set any SQLite encryption extension. Protection of the file at rest is the responsibility of the iOS platform (file protection classes) and the application layer.

On iOS, the app's documents directory uses Data Protection class NSFileProtectionCompleteUntilFirstUserAuthentication by default. The containing Zodl application may configure stricter protection. This is outside the scope of the engine itself.

15.5 No telemetry

The engine contains no analytics, crash reporting, or telemetry code. There are no calls to any analytics SDK, no HTTP requests to any endpoint other than the configured lightwalletd server, and no persistent identifiers (the accounts.uuid column is a local-only opaque identifier stored in the wallet database and never transmitted). This is verifiable by inspection: grpc.rs is the only file that opens outbound connections, and it contains only the lightwalletd gRPC methods.

15.6 Correlation analysis and recommendations

A lightwalletd operator who serves multiple wallet users can correlate wallets by the combination of:

  • Source IP address
  • GetBlockRange start height (birthday)
  • GetBlockRange end height trajectory over time (sync progress)
  • Transparent address set (revealed during enhancement)
  • Transaction IDs queried via GetTransaction

Users who share a lightwalletd server are distinguishable from each other by their range patterns and transparent addresses. This is a property of the lightwalletd protocol, not specific to Slipstream.

Recommendations for users and operators who want stronger privacy:

  • Server choice: use a self-operated or trusted lightwalletd. The engine is server-agnostic and accepts any compliant endpoint.
  • Tor: enabling Tor (a host-wallet setting) routes the wallet-identifying calls over isolated Tor circuits, unlinking them from the syncing IP (§15.3). The bulk download stays direct by design, so the IP + range remain visible on it — hiding those too requires a system-level VPN/Tor.
  • Transparent address use: wallets that use only shielded addresses leak significantly less during enhancement (no GetTaddressTxids calls, no GetAddressUtxos calls for those accounts, since get_transparent_receivers would return an empty set).

Known limitations

  • The bulk block download stays direct even with Tor on (deliberate parity with the old SDK; §15.3), so the syncing IP + birthday range remain visible to the operator. The wallet-identifying calls are Tor-isolated when Tor is on.
  • The 4-stream parallel fetch creates a fingerprintable traffic pattern not present in single-stream clients. This is an inherent consequence of the parallel fetch design and is acknowledged.
  • The TransactionsInvolvingAddress open-ended range requests (those with no block_range_end) are currently skipped. When this skip is removed and full transparent address scanning is implemented, the set of transparent addresses and ranges sent to the server will increase.
  • The privacy properties described here apply to the engine's own network behaviour. Privacy properties of the application layer, user-generated data, or any other SDK components are outside the scope of this analysis.
