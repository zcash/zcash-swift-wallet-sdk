The Data-Model Contract

Part I — Overview  ·  estimated reading time: 10 minutes

1-minute summary

Decision D3: Slipstream writes into the same data.db as the old SDK, with byte-identical rows in every table — verified by a golden-oracle harness. The only permitted non-determinism is one column (accounts.uuid), and that exception is grounded in the upstream source code. This contract is what makes the wallet openable by either engine, and the spend path unaffected.

The contract (D3)

Decision D3, locked in the roadmap: "The wallet data model does not change. Engine writes through zcash_client_sqlite into the same data.db."

What this means in practice:

  • Every table that upstream's scan_cached_blocks writes — blocks, nullifier_map, tx_locator_map, sapling_tree_shards, sapling_tree_checkpoints, orchard_tree_shards, orchard_tree_checkpoints, scan_queue, and all other zcash_client_sqlite tables — must contain exactly the same rows after a Slipstream sync as after an old-SDK sync over the same block range.
  • "Same rows" means same multisets: every row present in one database must be present in the other, with the same column values (except for the ALLOWLIST). Row order is not required to be identical; only set membership matters.
  • The schema itself is completely unchanged. Slipstream adds no new tables, no new columns, no schema version bumps.

Why byte-identity matters

The D3 contract is not just about tidiness. It has three load-bearing consequences:

1. Old-SDK openability

A wallet synced with Slipstream can be opened by the old SDK without migration, because the old SDK's ZcashRustBackend reads from the same data.db schema. If the schemas diverged, the app would be locked to one engine. The D3 contract keeps the two engines interchangeable.

2. The upstream brain keeps reading and writing

As described in chapter 2, functions like suggest_scan_ranges, get_wallet_summary, and fully_scanned_height all read from data.db. The spend path — propose_transfer, PCZT construction — writes the prepared transaction back to data.db. If Slipstream's writes were structurally different from upstream's, these functions would read incorrect state or write conflicts. Byte-identity ensures all upstream reads remain correct.

3. The spend path is untouched

Note witnesses, nullifiers, and the commitment-tree frontiers that the spend path needs to construct proofs are stored in data.db by scan_cached_blocks. A wallet synced with Slipstream's sparse persistence path (chapter 7) must have exactly the same tree shard blobs as a wallet synced via the upstream path — otherwise proof construction would fail. The oracle tests verify this down to individual shard blob bytes.

What "semantically identical" means

The oracle in slipstream/core/src/oracle.rs defines the comparison precisely. Two databases are semantically identical if, for every table that appears in either schema:

  • The set of column names is the same (minus ALLOWLIST columns, which are excluded from comparison).
  • The multiset of rows is the same — for each row in database A, an identical row exists in database B, and vice versa. Multiplicity matters: a duplicate row in A that is not in B is a difference.
  • Views are excluded from comparison (they are derived from the tables; if tables are identical, views are identical).

The comparison is canonicalised by converting every cell value to a string representation and collecting the (sorted) per-table sets. This is implemented in oracle.rs and called by the CLI oracle subcommand and the darkside oracle tests.

Oracle verification record (STATE.md, T6.4, T6.5, T6.8-S, T6.8-H2)
  • Hermetic oracle: 3×1000 block synthetic chain with the sparse path on and off — VERDICT IDENTICAL at every run.
  • Darkside oracle (T6.4): real-transaction fixtures; two full syncs (upstream vs sparse) — VERDICT IDENTICAL, including 2 transactions found and correct balance.
  • Mainnet 50k oracle (multiple runs): tipmost 50,009 blocks on mainnet, 26 tables compared — VERDICT IDENTICAL. Most recently at tip 3,375,336 (T6.8-H2).
  • Truncate-rescan oracle (T6.5): initial sync A (upstream) and B (sparse), truncate both, re-scan both from birthday — VERDICT IDENTICAL. Proves reorg/truncate compatibility.

All oracle runs cite the 26-table clean set: blocks, nullifier_map, tx_locator_map, sapling_tree_shards, sapling_tree_checkpoints, orchard_tree_shards, orchard_tree_checkpoints, scan_queue, schemer_migrations, and all others.

The ALLOWLIST — the only nondeterminism

The oracle ALLOWLIST is defined in oracle.rs and currently contains exactly one entry:

// slipstream/core/src/oracle.rs
pub const ALLOWLIST: &[(&str, &str)] = &[("accounts", "uuid")];

The accounts.uuid column is excluded from comparison because it is set to a fresh Uuid::new_v4() at account-import time. The write site is in the upstream codebase:

// zcash_client_sqlite-0.21.0/src/wallet.rs:464
let account_uuid = AccountUuid(Uuid::new_v4());

This is non-deterministic by design: the UUID is an opaque stable per-account identity, not part of the scan output. Its value does not affect note scanning, balance computation, nullifier derivation, or any aspect of wallet correctness. Oracle correctness is unaffected because all scan tables remain clean.

ALLOWLIST discipline

The comment in oracle.rs says "Keep EMPTY until the determinism test proves a column is non-deterministic; every addition needs a Decision-Log entry citing the upstream write site." The UUID entry was discovered empirically during T6.2 baseline testing and is the only entry. Adding to the ALLOWLIST is a deliberate act requiring a Decision-Log entry — it is not done speculatively.

How the contract is enforced: the golden oracle

The oracle is not a passive report — it is a hard gate. The T6.4/T6.5 correctness pass required the following before the sparse persistence path was turned on by default:

  1. Hermetic oracle: a fully in-process test (sparse_path_matches_upstream_on_synthetic_chain in oracle.rs test suite) that synthesises a 3×1000-block chain, scans it with both paths, and calls semantic_diff. This is in the standard cargo test suite — it runs in CI and locally.
  2. Darkside oracle: a #[ignore] test (sparse_pipeline_matches_upstream_on_darkside_fixture in darkside_oracle.rs) that uses a real lightwalletd darkside instance with known-transaction fixtures. Requires a running lightwalletd to execute.
  3. Mainnet oracle CLI: the slipstream-cli oracle subcommand syncs the same range twice (path A = upstream, path B = sparse), then calls semantic_diff and prints VERDICT IDENTICAL or DIFF. This is a manual gate run before each major change to the persistence path.
  4. Mutation tests: identical_dbs_diff_clean, row_delta_is_detected, duplicate_row_multiplicity_is_detected, missing_table_is_detected — these prove the oracle itself can detect deviations. Without them, a buggy oracle might report IDENTICAL for genuinely different databases.

Chapter 13 covers the oracle in full detail. This chapter explains why it is needed.

Two paths, one database

Migration story

There is no migration. Because Slipstream writes the same schema the old SDK reads, a user switching between engines does not need to re-sync or touch their wallet files. The engine selection is purely at the Swift layer — the same data.db is used by both.

Forward compatibility also works: if a future SDK version adds a schema migration, both engines will encounter the same schema version at open time, and both will apply it (through the same upstream migration logic in zcash_client_sqlite).

What the oracle does not prove

Honest limits of VERDICT IDENTICAL
  • It proves row identity, not note spendability directly. A separate spendability gate (chapter 13) is needed to confirm that found notes are actually spendable. The oracle confirms that the tree shard blobs are identical — the spendability gate confirms they are correct.
  • The oracle runs on controlled ranges. The mainnet oracle runs over tipmost 50k blocks (recent, low-density). The sandblasting era (1.70M–2.00M blocks) has been traversed on Mac (84,964 blocks IDENTICAL), but has not yet been verified by a full-range device oracle pass.
  • It does not cover the spend path. The oracle verifies that scanning produces identical data. It does not synthesise a spend transaction and verify the proof. The spend path correctness rests on the fact that the data it reads (witnesses, frontiers) is identical — which is what the oracle verifies.
  • Views are excluded. The oracle compares base tables. Views (like v_sapling_received_notes) are derived — if tables are identical, views are identical — but they are not independently verified by the oracle.

Known limitations

Data-model gaps
  • At-rest encryption is app-level: Slipstream inherits the old SDK's approach — data.db protection is the responsibility of the application. The engine provides no additional at-rest encryption.
  • No crash-recovery test beyond WAL semantics: Slipstream relies on SQLite's WAL mode for crash safety. The argument is that a partial write (an incomplete transaction) is rolled back on next open. There is no specific test that simulates a crash mid-chunk and verifies the database is consistent after recovery.
