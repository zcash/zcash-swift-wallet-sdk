12. Failure Model & Resilience

Estimated reading time: 15 minutes

1-minute summary

A sync frozen forever at 3.7% — state "Syncing", zero logs, zero error events, zero movement — was the failure that drove this chapter. The diagnosis: a stalled-but-open gRPC connection had no deadline, so the engine waited indefinitely; and a silently-dying tokio task had no supervisor, so a panic left state permanently stuck. The response was layered: deadlines on every network await, a supervisor task that converts panics to structured errors, a global panic hook that writes to device logs regardless of the log facade, a pass-level bounded retry for transient transport failures, and a Swift watchdog that makes any future silent freeze immediately visible. A subsequent validation run hit three simultaneous stream stalls and recovered from all three without intervention.

The 3.7% freeze story

Field report, 2026-06-12: a birthday-935,000 wallet restore frozen at exactly 3.7% — which, given the 270,109-block sync window and 10,000 blocks per chunk, corresponded precisely to one chunk having been scanned. The state counter showed "Syncing." No further log entries. No error event. The sync task had either hung waiting on a network call that would never complete, or had panicked silently and left the state machine without any cleanup path.

Investigation confirmed two independent structural causes. First: the treestate prefetch spawned for the next chunk boundary awaited GetTreeState with no deadline. A NAT rule or load-balancer silently dropping the flow would cause this await to hang indefinitely — the engine state would claim "Syncing" forever with frozen progress counters and zero log output. Second: tokio spawned tasks swallow panics; the panic only surfaces through the JoinHandle, which nothing was inspecting. A panic in the scan kernel (inside rayon::join, re-entered via block_in_place) would produce a dead task and a state machine stuck at "Syncing" with no way to ever reach "Error" or "Done".

The hardening response addressed both causes structurally — not with workarounds. Four orthogonal measures (B1–B4), all shipped in ENGINE_BUILD=2026-06-13.hardening1.

Error taxonomy and is_transient

Slipstream's error type (error.rs) has seven variants. The is_transient() predicate partitions them into retryable and non-retryable, with exhaustive test coverage (7 tests at error.rs:70–107):

Variantis_transient()Rationale
Transport(String) true Timeout, connect failure, stream stall — retrying with a fresh connection may succeed
Config(String) false Bad configuration; no amount of retrying fixes this
Wallet(String) false DB or scan logic error; retry would hit the same error
ScanContinuity{at} false Handled internally by the reorg recovery arm (chapter 10); never escalates
Discontinuity{at, detail} false Fetch continuity bug; retrying would loop on the same invalid data
MisbehavingServer false Bad proto or decode error — not a transport transient
Stopped false Engine lifecycle; not a retryable condition

This partition drives two separate retry systems: the per-fetch-chunk retry (reconnects on any Transport error at the worker level) and the pass-level retry (only fires when is_transient() == true). ScanContinuity being non-transient is intentional: it has its own dedicated recovery arm in the scheduler (chapter 10) and must never enter the pass-level retry path.

Three retry layers

Failures are caught at three concentric layers. Outer layers only see what inner layers cannot handle. Each layer maintains state and does not restart progress from zero unnecessarily.

Layer 1: stream deadlines and resume-from-height

The fetch workers (fetch.rs) apply two independent deadlines:

  • STREAM_IDLE_TIMEOUT = 30s (grpc.rs:40): fires if a gRPC stream delivers no messages for 30 seconds. A truly stalled stream dies here before the sub-chunk deadline.
  • UNARY_TIMEOUT = 30s (grpc.rs:35): applied to the response headers of streaming calls and to every unary call. A server that accepts but never answers fails fast.
  • Sub-chunk progress deadline (120s, FetchPlan::chunk_timeout): bounds accumulation of one sub-chunk; resets on every sub-chunk emission. Detailed in chapter 11.

On any Transport error, the worker retries from cursor.resume_from (the height after the last successfully emitted sub-chunk). Up to 3 zero-progress retry attempts per plan chunk; an attempt that made any progress resets the zero-progress budget. Reconnects on every retry (never reuses a potentially wedged channel).

Layer 2: treestate unary retry with fresh connections

The field evidence for this gap was direct: a mid-sync failure at 6.1% with the log line transport: get_tree_state: timed out after 30s — one GetTreeState call failed, and the whole sync was dead. Before the fix, GetTreeState calls in the scan path had zero retries.

The fix (grpc::retry_get_tree_state, grpc.rs:76–104) wraps all treestate calls in the scan path with up to TREESTATE_RETRY_MAX=2 additional attempts (3 total). Crucially, each retry opens a fresh gRPC channel (grpc::connect) to avoid reusing a potentially wedged connection. Backoff: 1 second then 3 seconds. Only is_transient() errors retry; decode/proto/logic errors propagate immediately.

This fix is applied in two places in scan.rs:

  • Initial seed (scan.rs:174): the treestate at range_start − 1 that seeds the first chunk's scan. A failure here was previously fatal to the entire range.
  • Per-chunk-boundary prefetch (scan.rs:235): the treestate prefetched while the current chunk scans. Spawned as a separate task so the fetch/scan overlap is preserved; the retry happens inside the spawned task.

Layer 3: bounded pass-level retry

If a Transport error escapes the fetch pipeline and scan path entirely — for example, if all three Layer 2 treestate retries fail — the pass-level retry in rust/src/lib.rs catches it. Constants:

  • PASS_RETRY_MAX = 2 (3 total attempts)
  • Sleep 5 seconds before attempt 2, 15 seconds before attempt 3
  • Only is_transient() == true errors retry
  • SyncState stays Syncing during retries — the UI does not see a flicker to error state for a transient condition
  • SyncStarted (tag=1) is emitted exactly once before the loop, not on each retry

Progress semantics across retries: begin_pass() at each sync_once entry resets the ratio counters (scanned/fetched/pass_total/range_end/spendable). This is correct because suggest_scan_ranges returns only the remaining unscanned ranges on re-entry, so the denominator recomputes from remaining work. The monotonic delta counters (enhanced_txs, ranges_completed, reorgs_recovered) are intentionally not reset — progress observers see continuous growth rather than resets on the individual fields. The brief "%" reset on total progress is an acceptable UX tradeoff for a rare event noted in STATE.md.

Panic containment

Before hardening, tokio spawned tasks swallowed panics silently. The JoinHandle would carry the panic information, but nothing inspected it. A panic anywhere inside the sync task — including in rayon thread-pool workers re-entered via block_in_place — would cause the task to die with state stuck forever at "Syncing".

B1: supervisor task

The fix (ffi_handle::spawn_supervised, ffi_handle.rs:120–158) spawns the sync task alongside a supervisor task that owns its JoinHandle. When the supervised task finishes:

  • Normal completion (Ok(())): the supervisor does nothing — the task body already set the state to Done or Error.
  • Cancellation (JoinError::is_cancelled()): the supervisor does nothing — the canceller (stop/free/restart) already set the state to Idle.
  • Panic (any other JoinError): the supervisor extracts the panic message, logs tracing::error!(panic = %panic_msg, "slipstream sync task PANICKED"), sets SyncState::Error(2), and pushes a tag=4/value=2 event to the ring. Silent death is now structurally impossible.

The abort handle returned by spawn_supervised is stored in the handle's task field — stop/free/restart only need to abort the task, not inspect it. Three unit tests verify the three completion paths (ffi_handle.rs:337–422).

B1: global panic hook

A second line of defence: at zcashlc_slipstream_open time (lib.rs:4405), install_slipstream_panic_hook() is called once per process (via std::sync::Once). It installs a chaining panic hook that reports every Rust panic through tracing::error! before delegating to the previously-installed hook. This ensures panics appear in os_log / device logs regardless of how the log facade is configured — the previous log_panics hook required the tracing-log bridge and the right log level. The chaining preserves test-harness hooks.

B2: deadlines on every network await

Every gRPC call in the engine now carries a deadline. The two constants (grpc.rs:35–40):

  • UNARY_TIMEOUT = 30s: applied via with_unary_timeout to every unary call: get_lightd_info, get_latest_block_height, get_tree_state, get_subtree_roots, and the streaming call setup for get_block_range, get_taddress_txids, get_address_utxos.
  • STREAM_IDLE_TIMEOUT = 30s: applied via next_with_idle_timeout to every stream.next() call on server-streaming responses.

Additionally, grpc::connect sets a 10-second connect timeout. No await in the network layer can hang indefinitely.

Two unit tests (grpc.rs:320–357) use start_paused = true (tokio's mock clock) to verify that stalled futures actually fire the timeout rather than hanging indefinitely.

Stall watchdog (Swift, B4)

The Rust-side measures make silent freezes structurally impossible for the cases they cover. The Swift stall watchdog catches any residual case — a future codepath, a race window, or a hang in code outside the engine — and makes it immediately visible without auto-restarting anything.

The watchdog (SlipstreamSynchronizer+StallWatchdog.swift) runs on every poll tick (every 2 seconds). It tracks the "progress signature" — a tuple of all engine progress counters: (fetchedBlocks, scannedBlocks, enhancedTxs, rangesCompleted, chainTip). When two consecutive snapshots have equal signatures while state == 1 (Syncing), and the elapsed time since the last change exceeds the 120-second threshold, the watchdog fires one loud Logger.error per stall episode carrying the full last snapshot. The 120-second threshold is chosen conservatively: the slowest observed device chunk is ~36 seconds on iPad A10, and progress counters advance within that window.

The watchdog re-arms (resets watchdogStallLogged) as soon as any counter moves again. It never restarts the engine — recovery policy stays entirely with the app layer.

The validation run

Field validation — STATE.md, T6.8-H2 session log, 2026-06-12

After shipping the hardening (B1–B4) and the transient-error retries (Layer 2 + Layer 3), the server-weather probe run produced 6/6 fresh 50k-block restores CLEAN on Mac (3× zec.rocks + 3× eu.zec.rocks) with zero stalls or failures. The subsequent acceptance run, combined with the sandblasting fix, hit 6 server EOF cuts through the spam era — all recovered via Layer 1 resume-from-height, zero escalation to Layer 2 or Layer 3.

The claim "survived 3 simultaneous stream stalls" is based on the 6 EOF cuts observed during the spam-era acceptance run: in a four-worker parallel fetch, multiple workers can encounter EOF simultaneously. All six were resolved at Layer 1 (resume-from-height) with no pass-level retry required.

The follow loop (T8.1) and its consequences

Slipstream's runner was single-shot through T8.0: sync_once ran one complete pass (fetch all suggested ranges, scan, enhance), then returned. T8.1 (ENGINE_BUILD=2026-06-14.t81-follow) ships in-foreground tip-following: after each successful pass, sync_body now enters a jittered [10–30 s] probe loop. A cheap engine::probe_tip (single GetLatestBlock) checks whether the server tip advanced; when it does, a full keyless catch-up pass runs. The loop is cancelled by the existing AbortHandle on stop() / free() / restart(). Mempool detection (GAP 1) remains a separate T8.2 item.

T8.1 shipped — follow-loop consequences

The catch-up pass has two observable UX properties: (1) A reorg that arrives after an initial sync will be detected on the next catch-up pass (suggest_scan_ranges returns Verify-priority ranges). (2) Progress percentage briefly resets to ~0 at the start of each catch-up pass (begin_pass() resets ratio counters — Deviation D4). Tip-gating means this flap only fires when a real block arrived; frequency ≈ mainnet block rate (~75 s). Chapter 19 records the full deviation record (D3/D4).

Known limitations

Honest gaps
  • Single-shot runner: no in-foreground tip-following; the wallet only updates on explicit sync calls. A reorg or new transaction arriving after a pass completes is not seen until the next pass.
  • Progress % resets on Layer 3 retry: the ratio counters reset when begin_pass() is called at each retry entry. The user briefly sees a lower percentage before it recovers. Monotonic counters (ranges_completed, enhanced_txs) do not reset.
  • Stall watchdog is visibility-only: the watchdog fires a log entry but does not attempt any recovery. Recovery policy is entirely with the app layer. If the app is backgrounded during a stall, the watchdog fires when the app returns to the foreground and the next poll tick runs.
  • A10 spam-era memory tuning pending: Layer 1 resume-from-height handles the bytes in flight, but the per-range in-memory shardtree plus decode amplification may exceed 2 GB on A10-class devices during the spam era. See chapter 11.
