14. Security Analysis

1-minute summary · reading time ≈ 10 min

Slipstream's security posture rests on four pillars: TLS with webpki roots for every server connection; multi-layer continuity checks that make serving wrong blocks detectable; a Rust implementation that confines memory-unsafe code to a narrow, documented FFI boundary; and a dependency surface limited to pinned upstream zcash crates with no vendored forks. This chapter characterises the threat model, documents what the engine validates versus trusts, and tells an auditor where to start.

14.1 Threat model

AdversaryCapabilityIn scope
Malicious or compromised lightwalletdServes crafted blocks, wrong tree states, withholds data, returns garbage in gRPC responsesYes
On-path network attackerIntercepts TCP, downgrades TLS, injects responses, drops packetsYes
Malicious chain dataBlocks with maximally-sized outputs, adversarial compact formats, reorg sequences designed to confuse the scannerYes
Compromised device or OSFull read/write access to device storage and memoryNo — out of scope
Malicious app hostThe iOS app embedding the SDK feeding crafted arguments to the engineNo — out of scope; the SDK trusts its caller

The engine does not defend against device compromise. A device with OS-level access can read data.db directly or inject code into the process. Protection at that level is an iOS platform responsibility (file protection classes, Secure Enclave for keys). The engine's job is to behave correctly when the server is hostile and the network is adversarial.

14.3 What the engine validates

TLS transport

Every connection to lightwalletd is opened in grpc.rs via tonic with ClientTlsConfig::new().with_webpki_roots() (line 147). This uses the rustls TLS implementation and the webpki-roots certificate bundle — the same trust roots used by the upstream tor.rs module. There is a 10-second connect timeout (connect_timeout(Duration::from_secs(10)), line 143). Plain-text connections are possible only when endpoint.tls == false, which is only set for local darkside tests and explicit CLI --no-tls usage.

A network-level downgrade attack (stripping TLS) would cause the connection to fail at the TLS handshake layer rather than silently fall back to plaintext — rustls does not implement TLS downgrade fallback.

Block continuity (transport layer)

verify.rs implements Continuity::verify_blocks, which checks two invariants on every received chunk before it enters the queue:

  1. Heights are consecutive: b.height == last_height + 1
  2. Hash chain: b.prev_hash == last_hash (when both are non-empty)

A gap or prev-hash mismatch produces SlipstreamError::Discontinuity { at, detail }, which causes the fetch task to abort and propagate the error to the scheduler. This check runs at the transport layer, before any block reaches the scanner. The prev-hash check degrades to heights-only if a server strips prev_hash from responses — this is noted in the code comment at verify.rs:29–33.

Wallet-level continuity (scan layer)

A second continuity layer operates inside scan_cached_blocks (upstream). When the scanner detects that a block's prev_hash does not match the last scanned block, it raises a continuity error that scan.rs maps to SlipstreamError::ScanContinuity { at }. The scheduler's recovery arm handles this structured error by truncating the wallet DB and re-queuing affected ranges — see Chapter 10.

Server treestates: trusted then cross-checked

GetTreeState responses (used for chunk-boundary frontiers and for the wallet birthday treestate) are trusted at fetch time — the engine does not independently verify the treestate content against any commitment it holds before scanning from it. However, they are not simply accepted without any verification:

  • If the treestate is subtly wrong (inconsistent tree size, corrupted frontier bytes), the upstream scan_cached_blocks kernel will raise an error when it tries to extend the tree from an invalid frontier.
  • If the treestate is wrong in a way that changes the scan output, the oracle would detect the divergence — a wrong frontier produces wrong shard bytes, which differ from the upstream path's correct shards.
  • ScanContinuity errors triggered by a wrong treestate are non-transient (is_transient() == false), so they fail the pass rather than being silently retried.

The precise claim: a server-controlled wrong treestate that silently produces a wallet-consistent-but-factually-wrong scan result (one that passes all internal checks and the oracle) cannot be ruled out from the transport layer alone. Trust in the treestate ultimately rests on TLS channel authentication and the honesty of the lightwalletd operator — the same trust assumption as the upstream SDK.

MisbehavingServer error class

SlipstreamError::MisbehavingServer is raised in transparent.rs when server UTXO responses contain out-of-range values (invalid txid slice length, negative zatoshi, height overflow, unknown recipient address). This is classified as non-transient — it does not retry. The wallet records it as an error rather than silently ignoring potentially adversarial UTXO data.

Deadlines and resource bounds

Every gRPC call carries a deadline (B2, shipped in the hardening1 build). The constants from grpc.rs:

  • UNARY_TIMEOUT = 30s — hard deadline for any unary call (GetTreeState, GetTransaction, etc.)
  • STREAM_IDLE_TIMEOUT = 30s — per-message deadline for streaming calls; 30 seconds of silence on an open stream is classified as a stall and raised as SlipstreamError::Transport
  • Connect timeout: 10 seconds (grpc.rs line 143)

These prevent a hostile server from hanging the engine indefinitely by holding an open connection without delivering data. Resource bounding is covered in detail in Chapter 16.

14.4 Memory safety posture

The entire sync engine (slipstream/core/) is written in Rust. The Rust type system and borrow checker enforce memory safety — there are no raw pointer dereferences, buffer overflows, or use-after-free possibilities in safe Rust code. The rayon parallel sections in persist.rs use Rust's data-race-free parallel iterator model; the tokio async runtime enforces send/sync bounds at compile time.

Unsafe code at the FFI boundary

Unsafe Rust is confined to the C FFI functions in rust/src/lib.rs. The six Slipstream FFI functions (zcashlc_slipstream_open, _start, _stop, _snapshot, _drain_events, _free) all use the established unwrap_exc_or / catch_panic pattern from the existing libzcashlc codebase. The specific unsafe operations in these functions are:

  • Pointer-to-slice conversion: slice::from_raw_parts(db_data, db_data_len) and equivalent for server_host and ufvk parameters — each with explicit safety contracts in the function's # Safety doc-comment requiring non-null, valid-for-reads, alignment-1 pointers.
  • Pointer-to-reference conversion: handle.as_mut() and handle.as_ref() on the opaque handle pointer — null-checked before use; null handle returns a default/error value rather than dereferencing.
  • Box reconstruction: Box::from_raw(handle) in zcashlc_slipstream_free — only called when the handle is non-null, re-taking ownership of a pointer originally produced by Box::into_raw.
  • Buffer write: std::ptr::copy_nonoverlapping(drained.as_ptr(), *buf, to_copy) in drain_events — guarded by the caller's safety contract that buf is valid for writes for buf_len elements.

None of the slipstream/core/ modules contain any unsafe blocks. All unsafe code is in rust/src/lib.rs at the already-audited FFI boundary used by the rest of libzcashlc.

No unwrap/expect in engine core

Per CONVENTIONS.md, unwrap() and expect() are forbidden in non-test engine code. The persist.rs rayon join closures return Result; both results are checked after the join via sap_result?; orch_result? (no unwrap). The one expect("always Some") in build_subtrees is in the hot loop that takes elements from a &mut [Option<T>] slice that was populated with Some values on every entry — it is structurally infallible and documented as such.

14.5 Panic policy

Panics are not silently swallowed. The B1 hardening (shipped in the hardening1 build) installs a tracing panic hook in install_slipstream_panic_hook() at zcashlc_slipstream_open time. The hook calls tracing::error!(panic = %info, "rust panic"), which routes through the iOS logging infrastructure, then chains to the previous hook (preserving test harness hooks). The sync task is wrapped by ffi_handle::spawn_supervised, which inspects the JoinHandle and maps a panic to SyncState::Error(2) plus a tag=4/value=2 ring event — see Chapter 12 for the full panic containment design.

The engine depends on the following upstream zcash crates, all pinned in Cargo.lock:

There are no vendored forks of any zcash crate. All additions to the dependency surface require a decision-log entry per the allowlist protocol (Decision Log 2026-06-11, T6.3 entry). The shardtree, incrementalmerkletree, and zip32 crates were promoted to direct dependencies as part of T6.3 — they were already transitive dependencies; promoting them to direct deps is transparent in the lockfile.

14.7 Where an auditor should start

For an auditor reviewing Slipstream for the first time, this is the suggested reading order by risk surface:

  1. The oracle harness (slipstream/core/src/oracle.rs) — understand what byte-identical means and verify the mutation tests. If the oracle is trustworthy, the persistence correctness story rests on solid ground.
  2. The FFI boundary (rust/src/lib.rs, lines 4355–4714) — all unsafe code, the panic hook, the supervised spawn, the pointer/slice contracts.
  3. Fetch resume logic (slipstream/core/src/fetch.rs) — specifically the sub-chunk resume-from-height path: verify that a retried chunk cannot send blocks twice (double-scan impossibility argument).
  4. Persist transactionality (slipstream/core/src/persist.rs, sparse_put_blocks) — the inner.transactionally closure that wraps both the row writes and the tree flush; verify that a crash mid-write leaves the database in a state the scan queue can recover from.
  5. Error transience classification (slipstream/core/src/error.rs, is_transient) — verify that only Transport errors retry; all others (including MisbehavingServer, ScanContinuity, Wallet) are non-retrying.

Known limitations

  • The prev-hash continuity check in verify.rs degrades to height-only when a server omits prev_hash from GetBlockRange responses. This is noted in the code.
  • Server treestates are trusted at fetch time; there is no independent local derivation of the expected frontier. This is a protocol-inherent limitation shared with the upstream SDK.
  • TLS certificate revocation is not checked (webpki-roots provides root trust; CRL/OCSP checking is not wired in tonic 0.14.6).
  • The engine has a single retry path for transient transport errors; a persistent server that always times out can exhaust PASS_RETRY_MAX (2 retries) and leave the wallet in an error state (displayed to the user, not silent).
