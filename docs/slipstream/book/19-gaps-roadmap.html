19. Known Gaps & Roadmap

Part V — Evidence & Process  ·  estimated reading time: 16 minutes

1-minute summary

This is the canonical list of what Slipstream does not yet do, why each item matters, what the current mitigation is (if any), and what the planned fix looks like. Nothing is softened. Items come directly from the STATE.md Blockers section, the decision log, and the PLAN.md honesty register. A status column uses four values: Open (no mitigation, user-visible impact), Mitigated (partial — the problem is bounded but not solved), Queued (design decided, next in sequence), and Parked (deferred by user request, revisit planned).

19.2 Open gaps — user-visible today

Mempool detection missing (P8 GAP 1)

User-reported, 2026-06-12

Sending ZEC from a non-Slipstream wallet to a Slipstream wallet shows no incoming transaction until the transaction mines AND a new sync pass starts. The old SDK has integrated mempool monitoring via lightwalletd's GetMempoolStream RPC, with decryption via decrypt_and_store_transaction.

Why it matters: For interactive use — especially receiving payments — the absence of pending-transaction state is a significant UX regression vs. the old SDK. A user who sends ZEC to a Slipstream wallet sees nothing until the next full sync pass completes.

Current mitigation: None. The engine is single-shot and does not monitor the mempool at any point.

Planned fix shape: Engine-level mempool stream while at tip: stream GetMempoolStream, decrypt+store via decrypt_and_store_transaction, emit foundTransactions. Pairs with GAP 2 (both are "engine only syncs once" symptoms). Targeted for P8.

No periodic tip-following (P8 GAP 2)

User-reported, 2026-06-12

The FFI runner is single-shot per start() call: one sync_once, then SyncState::Done until the app lifecycle triggers another start(). A wallet open in the foreground after an initial sync sees no new blocks arrive. The old SDK re-synced continuously on a timer.

Why it matters: Any wallet sitting at the home screen after an initial restore stops tracking the chain. New blocks — and any ZEC received — will not appear until the app is backgrounded and re-foregrounded (triggering a new lifecycle start).

Current mitigation: The pass-level bounded retry (PASS_RETRY_MAX=2, T6.8-H2) handles transient stalls within a pass, but does NOT implement periodic tip-following. begin_pass() (T5.6 review) already makes repeated passes counter-safe — the structure is ready; the trigger is missing.

Planned fix shape: Engine-level re-arm loop: sleep ~20–30 s at SyncState::Done, call sync_once again (cheap passes at tip: suggest_scan_ranges returns a tiny or empty range). Alternatively, a Swift-side restart-on-Done timer. Targeted for P8.

A10-class spam-era memory tuning

Recorded in Blockers, 2026-06-12 (T6.8-S)

Mac RSS grew from 1.31 GB to 1.84 GB traversing the spam era (mainnet ~1.70M–2.00M) with default budgets. iPhone 16 Pro (8 GB RAM) is expected to survive. iPad A10 6th Gen (2 GB RAM, shared with GPU) will NOT without tuning.

Why it matters: Old wallets — anyone who set a birthday before ~1.7M — cannot restore on A10-class devices without a jetsam kill. This is the most common iOS device class in the Zodl user base.

Current mitigation: The sandblasting era is traversable on Mac-class hardware (T6.8-S). A10-class is untested. CLI override: --chunk-split-bytes and --memory-budget-bytes.

Planned fix shape: Per-device-class configuration: smaller memory_budget_bytes (e.g. 64 MB) and chunk_split_bytes (e.g. 4 MiB) for A10-class. Consider range segmentation so the sparse tree state resets periodically, bounding in-memory accumulator size across a 1.5M-block historic range.

Tor not wired into Slipstream paths

Documented in ch. 15 (Privacy), PLAN.md honesty register

All Slipstream fetch, scan, and enhance traffic uses direct TLS to lightwalletd. The old SDK has Tor integration for some flows (GetBlock, GetTransaction, certain enhancement queries). Slipstream does not use these paths.

Why it matters: Users who enable Tor in Zodl expect all wallet network traffic to route through Tor. Slipstream's direct-TLS sync reveals the user's IP address and query patterns to the lightwalletd operator. This is the same leakage class as the old SDK without Tor enabled — but it is a regression from the Tor-enabled old SDK.

Current mitigation: None for Slipstream paths. The old SDK's Tor paths are intact and available if the user reverts to the old synchronizer.

Planned fix shape: P8 T8.x — route tonic connections through the arti channel already wired in the libzcashlc FFI boundary for the old SDK's Tor client. The arti client is already present as a dependency; the grpc connect() call needs an arti-backed transport channel variant.

TransactionsInvolvingAddress skip (completeness gap)

Enhancement path — open-ended skip documented in enhance.rs

Enhancement requests of type TransactionsInvolvingAddress with an open-ended block range (no block_range_end) are skipped silently with a warn! log. The transparent-address history query (GetTaddressTxids) would need an explicit range; the open-ended form does not map cleanly to the gRPC API.

Why it matters: Transparent address history may be incomplete in edge cases where the upstream WalletDb generates open-ended TransactionsInvolvingAddress requests. For most wallets using shielded addresses primarily, this is not observed in practice.

Current mitigation: Skips are deduplicated (per-run HashSet, T4.6) so each unique address+range combination produces only one warning. The final enhancement backstop runs post-loop.

Planned fix shape: Supply a concrete block range (e.g., birthday..current tip) for any open-ended request. Requires verifying that the upstream data_api generates these requests in a form where a closed range is semantically equivalent. Targeted for P8.

19.3 Mitigated gaps

startFailed(.rustSlipstreamNotOpen) launch wart

Zodl observed synchronizerStartFailed(.rustSlipstreamNotOpen) at app launch in T5.5 testing. The cause: some call path invoked start() before prepare() completed, hitting the FFI guard that requires an open handle. The error is benign — the app self-recovers when prepare() subsequently opens the handle and the lifecycle triggers another start(). Recorded for investigation of the Zodl initialization sequencing; low priority.

L2 row batching seam-blocked (upstream API)

zcash_client_sqlite 0.21's WalletDb::transactionally closure receives a private conn: C field (no public accessor) wrapping a rusqlite::Transaction. The L2 optimization — batching multiple put_blocks rows into a single multi-row SQL INSERT — requires access to the raw transaction handle to inject custom SQL. The seam is confirmed blocked (Decision Log 2026-06-12, T6.8-L3a gate 4). Estimated speedup: ~8–40 s on iPhone, ~40–80 s on iPad per truth-table attribution. Resolution requires either an upstream API change to publicize the transaction handle or a vendored fork of zcash_client_sqlite.

darkside ≥v0.5 retirement items

The current darkside lightwalletd (v0.4.9 in Tests/lightwalletd/) does not implement GetTreeState or GetSubtreeRoots. Slipstream works around this via: scan_chunks_from_treestate (accepts a synthesized ChainState instead of fetching one), seed_block_metadata (injects a 663149 block record with a fetched prev_hash), and a hardcoded SAPLING_TREE_128607 frontier. All three workarounds exist only in the darkside test path and do not affect production. When darkside upgrades to ≥v0.5 or zaino, these workarounds can be retired and the tests can use the real treestate RPC path.

19.4 Queued and parked items

L4b write-behind pipelining (SHIPPED flag-off — T6.9, 2026-06-12)

Shipped at T6.9 behind EngineConfig::write_behind (default off; CLI --write-behind). The crash-consistency requirement was met by keeping each deferred commit the EXACT sparse_put_blocks transaction (rows + tree + flush atomic, strictly serial, depth-1) on a persist lane that owns the per-range tree state; the scan's four DB reads are virtualized by a pending-aware facade and every read outside that surface fails loudly. Full design and citations: chapter 7's write-behind section.

Evidence so far: hermetic write-behind oracles CLEAN; darkside REAL-notes fixture oracle CLEAN (+3 more write-behind darkside variants green); mainnet tip−2000 oracle VERDICT IDENTICAL with --sparse-b --write-behind-b; Mac 50k A/B mean 6.79 s (off) vs 6.18 s (on) with persist_overlap_s ≈ 1.05 s — Mac is persist-bound per chunk (commit ≈ 790 ms vs decrypt ≈ 320 ms) so depth-1 can hide only the decrypt side there; the device balance (iPad ≈ 258 s persist vs ≈ 286 s decrypt; iPhone ≈ 42 s vs ≈ 43 s) is where the lever pays. The earlier ~6:15–6:45 iPad / ~60 s iPhone numbers remain projections, not measurements. Default-on flip waits on the device field A/B.

L4a decrypt-kernel / column-ECDH (PARKED — user request, 2026-06-12)

L4a is the Zkool-class lever: a column-oriented batched ECDH kernel that would replace the current per-note trial-decryption path (≈53% of device scan time / ≈286 s on iPad A10 T6.7). Parked at the user's request; the user asked to focus on L4b write-behind pipelining first. When revisited, L4a needs its own golden-oracle harness (the existing oracle compares output to the upstream scan_cached_blocks path; a custom kernel that produces different intermediate representations needs an equivalent correctness gate before any code ships).

shardtree merge_checked waste (PARKED — fork-tier)

The merge_checked function in shardtree-0.6.2 (prunable.rs:277-352) recomputes the root hash of both merge sides at every recursion level, discarding the result via .ok() + vacuous zip().all() when either side is incomplete — which is always true for the frontier path-tree. This contributes ~33% of per-chunk orchard tree time (~100–204 ms/chunk, proved by the T6.8-L3b tail-chunk measurement). The fix requires patching or forking shardtree (the same seam class as the L2 row-batching block). Parked pending upstream engagement or a deliberate fork decision.

Flag and productization decisions

Action required before any public release
  • WalletConfig.FeatureFlag.useSlipstreamSynchronizer.enabledByDefault = true must be reverted to false in Zodl's WalletConfig.swift after the user gives final sign-off. The TODO marker is in place. Local-only mode means this has not been pushed anywhere; the risk is a release build accidentally shipping with Slipstream enabled before the team is ready.
  • The LOCAL-ONLY designation (D9) means no pushes, no remote issues, no PRs to any remote repository. All commits carry the [#1755] tag as a local-only marker. A real public issue must be created if/when the user lifts the LOCAL-ONLY restriction.
  • Android path (P7): decoupled by user decision 2026-06-11. The slipstream-core crate is platform-neutral and designed to slot into an Android Rust backend. A uniffi or JNI binding layer is the integration task; no work has started.

19.5 Inherent limitations (not gaps)

These items are architectural constraints, not missing features. They are documented here for completeness.

  • Server trust: Slipstream trusts the server's treestate values until the scan itself verifies them through continuity checks. A malicious server can attempt to mislead the engine (see ch. 14 for the threat model and ch. 10 for the three detection layers). This is the same trust model as the old SDK and all lightwalletd-based wallets.
  • Transparent address leakage: Querying transparent address history via GetTaddressTxids reveals transparent addresses to the server. This is inherent to the protocol and documented in ch. 15. It is not a Slipstream-specific regression — the old SDK has the same leakage.
  • No telemetry: No analytics, crash reports, or telemetry of any kind are collected or transmitted. The engine emits structured logs via tracing to the device's os_log subsystem only.
