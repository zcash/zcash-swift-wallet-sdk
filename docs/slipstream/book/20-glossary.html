20. Glossary & Decision Digest

Part V — Evidence & Process  ·  estimated reading time: 18 minutes

1-minute summary

Two reference sections in one place. The Glossary gives the precise meaning of every term of art as used in this project — some terms have standard Zcash meanings that the engine uses differently. The Decision Digest gives D1–D9 (the locked strategic decisions) plus the major dated decisions from the STATE.md decision log, each with a one-paragraph rationale and a STATE.md date pointer.

20.1 Glossary

TermPrecise meaning as used in this project
AheadGate A semaphore-based admission-control structure in fetch.rs that limits how far non-floor fetch workers can run ahead of the reorder release point. Default budget: 8× chunk_split_bytes = 64 MiB. The floor plan chunk (the one currently being consumed by the scan side) is exempt and always streams freely. Without AheadGate, K−1 workers each streaming a multi-hundred-MB spam-era chunk would park hundreds of MB in the reorder buffer simultaneously. Added in T6.8-S.
always-green The discipline that cargo test -p slipstream-core -p slipstream-cli and swift test --filter OfflineTests must pass before and after every commit on the slipstream branch. A commit is the unit of resumability; no commit may break the test baseline. Defined in CONVENTIONS.md.
byte budget The memory bound placed on the in-memory chunk queue: the queue blocks producers when the total estimated byte size of queued chunks exceeds this limit. Configured via EngineConfig::memory_budget_bytes. Separate from the AheadGate (which bounds the reorder buffer, not the downstream queue). Both exist because the engine has two places where unbounded accumulation is possible.
checkpoint window The set of the newest 100 distinct checkpoint IDs retained by the commitment tree after pruning. "100" comes from PRUNING_DEPTH = 100 in zcash_client_backend ll/wallet.rs:52. The checkpoint window determines which blocks can serve as reorg rollback points. This definition mirrors upstream exactly.
checkpoint downgrade The T6.3b optimization in persist.rs that pre-converts doomed Retention::Checkpoint values to Marked or Ephemeral before they enter the in-memory ShardTree, skipping the ~9,900 create-then-prune checkpoint operations per 10k-block chunk. The resulting shard blobs are byte-identical to what upstream produces after its own prune cycle — proved by the golden oracle at three scale levels.
chunk (plan chunk) A contiguous range of blocks returned by suggest_scan_ranges and assigned to one fetch-worker slot by the scheduler. Default size: 10,000 blocks. A plan chunk may be split into multiple sub-chunks by the byte-budget splitter in dense eras. The Chunk struct in chunk.rs carries the accumulated blocks from one (plan) chunk's fetch plus its estimated byte size and continuity metadata.
chunk index The dense sequential integer assigned to chunks as they exit the reorder buffer and enter the scan queue. Starts at 0 for the first chunk of each pass. Sub-chunks inherit the plan chunk's index; the scan side sees a flat dense stream.
ChainState The commitment-tree frontier state returned by GetTreeState and accepted by scan_cached_blocks as its starting point for each chunk boundary. It encodes the Sapling and Orchard tree sizes and a commitment at the start height. Slipstream fetches one ChainState per chunk boundary via get_tree_state (with retry in retry_get_tree_state since T6.8-H2). The alternative — deriving it locally — was rejected in T2.3 because zcash_client_sqlite exposes no frontier read API.
darkside A special mode of lightwalletd (invoked with --darkside-very-insecure) that allows a test harness to stage arbitrary blocks and transactions. Used by the 10 darkside integration tests. NOT a production path. Enabled in slipstream-core behind the darkside cargo feature flag; all darkside tests are #[ignore] so they never run in CI's plain cargo test.
differ The semantic_diff function in oracle.rs that compares two wallet databases as canonical row multisets. It uses schema union (both databases contribute to the table list), column-level allowlist filtering, and canonical value encoding (NULL, integers as decimal, blobs as hex). A "VERDICT IDENTICAL" result means every non-allowlisted row in every table matches exactly.
ENGINE_BUILD A string constant in slipstream/core/src/engine.rs:25 (currently "2026-06-13.walltime") logged at every sync start and in every stage-split line. Used to verify that the device is running the expected engine binary, not a stale XCFramework slice. Must be bumped on every performance-relevant engine change. See the stale-framework incident in ch. 17.
frontier In the Zcash commitment tree, the path from the last committed leaf to the root. In Slipstream's context, insert_frontier (inside the sparse tree path in persist.rs) inserts the frontier annotation at the start of each chunk — the REFERENCE checkpoint that marks the boundary between "fully scanned" and "pending" in the ShardTree. This call has a fixed per-chunk cost (~100–204 ms orchard) caused by the merge_checked redundant-hashing issue documented in ch. 19.
hermetic A test that runs without any external dependencies: no network, no lightwalletd, no SQLite on disk. All unit tests in slipstream-core and slipstream-cli are hermetic by default. The stress binary is also hermetic (it uses in-memory structures only). Contrasted with "darkside" (requires local lightwalletd) and "mainnet" (requires internet + public server).
LOCAL-ONLY The user decision (2026-06-10, Decision Log) that the Slipstream branch is never pushed to any remote, no remote issues or PRs are created, and the prototype exists only on this machine. Lifted only by explicit user instruction. Commits use [#1755] as a local-only marker (GitHub never reuses issue numbers; #1755 was scrubbed on the remote).
oracle The correctness verification system comprising: the differ (semantic_diff), the hermetic synthetic oracle tests (in oracle.rs and persist.rs), the darkside oracle tests, and the CLI oracle subcommand that runs Path A (upstream) vs. Path B (Slipstream sparse) and prints "VERDICT IDENTICAL" or a diff. Three scale levels: hermetic (always-green), darkside (real notes), mainnet (50k+ real blocks). See ch. 13 for the full design.
pass One invocation of sync_once in the FFI runner. A pass: fetches the chain tip, runs the full suggest_scan_ranges → fetch∥scan → enhance cycle, then completes with SyncState::Done or SyncState::Error. Ratio-type progress counters (scanned, fetched, pass_total) reset at the start of each pass (via begin_pass()). Monotonic counters (enhanced_txs, ranges_completed, reorgs_recovered) persist across passes for the lifetime of the handle.
plan chunk See "chunk (plan chunk)". The "plan" prefix distinguishes a full suggest_scan_ranges assignment from a sub-chunk produced by the byte-budget splitter. A plan chunk's sub-chunks share the same plan_index.
range A contiguous scan assignment with an associated priority. Three priorities matter: ScanPriority::ChainTip (the most recent blocks, scanned first for spend-before-sync), ScanPriority::Historic (older ranges filled in afterwards), ScanPriority::Verify (continuity-check ranges at reorg boundaries, processed before all others). Priority ordering comes from suggest_scan_ranges — Slipstream does not decide priority, it follows the upstream scheduler.
ratio vs delta counters The two counter classes in the progress surface (T5.5/T5.6 design). Ratio counters (scanned_blocks, fetched_blocks, pass_total, range_end, spendable) are used for the 0–100% progress display and reset at each begin_pass() so restarts show honest remaining progress. Delta counters (enhanced_txs, ranges_completed, reorgs_recovered) are monotonic per handle lifetime, never reset, and used by Swift's lastEnhancedCount-style strict-greater comparisons for events like foundTransactions.
SbS (Spend-before-Sync) The scheduler strategy where ChainTip-priority ranges are scanned first. Because the most recent blocks are where the wallet's own notes most likely appear as spendable, scanning these before the historic backfill lets the wallet report a spendable balance much earlier than a strictly-sequential scan would allow. Implemented via upstream's suggest_scan_ranges priority ordering — not a Slipstream-specific feature, but central to why ChainTip ranges trigger the spendable latch.
shard / SHARD_HEIGHT In the Zcash commitment tree, a subtree of height SHARD_HEIGHT that is stored as a unit. The Sapling and Orchard shard heights are defined by SAPLING_SHARD_HEIGHT and ORCHARD_SHARD_HEIGHT from zcash_client_backend (imported in persist.rs:28). The sparse tree implementation uses a SparseShardStore that only loads the shards needed for the current chunk rather than the full tree.
spendable latch A flag in the progress surface (FfiSlipstreamSnapshot::spendable) that is set to true when a ChainTip-priority range completes scanning. Once set, it is never cleared within a pass. Its role: tell the Swift layer to refresh the wallet summary immediately, so the user sees their spendable balance as soon as the most-recent blocks are scanned, without waiting for the full historic backfill to complete. Implemented in scheduler.rs:303-309.
SparseShardStore The in-memory ShardStore implementation defined in persist.rs (T6.3–T6.4). Instead of reading and writing every shard to SQLite on each chunk, it seeds from the current stored shards at pass start and accumulates all mutations in memory. A single transactional flush writes the changed shards at chunk commit. The "sparse" label means only shards touched by the current chunk are loaded — not the full tree.
sub-chunk A slice of a plan chunk produced by the ChunkSplitter in fetch.rs. Sub-chunks have a maximum byte size of chunk_split_bytes (default 8 MiB). Each sub-chunk carries a (plan_index, sub_index) tuple and an is_last flag. The per-sub-chunk 120 s deadline replaces the old per-chunk 120 s deadline so that spam-era chunks with 1+ GB of wire data can never time out. The scan side sees sub-chunks as ordinary chunks (dense Chunk.index).
three-layer gotcha The build chain: Zodl → SDK (local package) → Rust (prebuilt XCFramework). Xcode never compiles Rust; it uses the prebuilt LocalPackages/libzcashlc.xcframework. A Rust change that is not followed by ./Scripts/init-local-ffi.sh + SPM cache reset + Xcode rebuild produces a device running the old binary. The ENGINE_BUILD tag is the detection mechanism. Defined in CONVENTIONS.md.
treestate The server's commitment-tree state at a specific block height, returned by the GetTreeState gRPC RPC. Slipstream fetches one treestate at the start of each scan chunk (with retry since T6.8-H2). The treestate seeds scan_cached_blocks's from_state parameter. The server's treestate is trusted-then-verified: the subsequent scan's continuity checks will detect any divergence between the server's claimed state and what the blocks actually produce.

20.2 Decision Digest — D1–D9 (locked)

These nine decisions were locked on 2026-06-10 and may not be re-litigated without a Decision Log entry in STATE.md. They are the architectural invariants that all subsequent design choices must respect.

#DecisionRationale (one paragraph)
D1 Engine lives in this repo as slipstream/core and slipstream/cli. All new work lives under slipstream/ (code) and docs/slipstream/ (docs). Permitted exceptions: root Cargo.toml workspace lines, CLAUDE.md pointer, P4 FFI exports in rust/src/lib.rs, P4 Swift files under Sources/ZcashLightClientKit/Slipstream/. Sharing the same repo means sharing the exact zcash_client_sqlite and zcash_client_backend crate versions — two separately-compiled static libraries including the same crate would collide in the iOS binary linker. It also reuses the XCFramework pipeline, the darkside test infrastructure, and the bundled checkpoints. The containment rule keeps old-SDK and Slipstream code unmixable, so a session working on Slipstream cannot accidentally break the old sync path. Amended 2026-06-10: includes Tests/OfflineTests/Slipstream* and Tests/DarksideTests/Slipstream* as enumerated exceptions.
D2 "Upstream brain, Slipstream body." Parallel tonic fetchers → bounded in-memory chunk queue → upstream scan_cached_blocks over a custom in-memory BlockSource → unchanged data.db schema. De-risking correctness for M1 was the overriding constraint. Using upstream's audited scan_cached_blocks means every note scanning, nullifier computation, and balance derivation is identical to the reference implementation — no custom kernel was needed to achieve the 6.9× speedup. The architectural bottlenecks (disk cache, serial fetch, connection churn, checkpoint churn) were all in the orchestration layer, not the cryptographic primitives.
D3 The wallet data model does not change. The engine writes through zcash_client_sqlite into the same data.db; the coverage ledger is the existing scan-queue in that database. A user constraint with correctness consequences: the upstream wallet brain (spend path, PCZT, summaries, key derivation) continues to read and write the same data.db. Any silent schema divergence would corrupt spend state or balances with no error surfacing at write time. The golden oracle (ch. 13) enforces this constraint mechanically — "VERDICT IDENTICAL" on every persistence change is the D3 enforcement gate.
D4 Swift seam = new SlipstreamSynchronizer: Synchronizer (additive file), implementing the ~10 sync members on the engine and delegating the ~40 data-model members to existing SDK components via the existing DIContainer. Zodl's dependency client already parameterizes on the Synchronizer protocol. Implementing the same protocol means zero app-surface change — the wallet team swaps synchronizer implementations behind a compile-time flag without touching any feature code. The delegation strategy for data-model members avoids duplicating the transaction, balance, and key derivation logic that the old SDK already implements correctly.
D5 CLI-first development. Every engine capability lands and is verified in slipstream-cli on macOS (cargo test + darkside lightwalletd) before any Xcode involvement. Phases 1–3 require no Xcode at all. macOS + cargo gives a deterministic, fast iteration loop. Xcode adds build-time indirection (SPM, XCFramework, code signing) that makes failures ambiguous. The CLI-first approach means every correctness and performance regression is surfaced by a hermetic cargo test invocation before the slower Xcode rebuild cycle begins. Performance benchmarks are CLI subcommands (reproducible in any session, from any machine with cargo).
D6 Engine is keyless: accepts UFVKs only; spend authority never enters the engine. Security posture from the original design document. The engine is a scanner, not a signer. Keeping spend keys out of the Rust engine boundary means a bug in the engine cannot exfiltrate private keys. Spend authority lives entirely in the old SDK's Swift/Rust signing path, which the Slipstream engine never touches.
D7 Engine owns a multi-thread tokio runtime per instance, created at zcashlc_slipstream_open and live until zcashlc_slipstream_free drops the Box<SlipstreamHandle>. stop() cancels only the sync task; the runtime remains for the next start(). Mirrors the TorRuntime precedent in rust/src/lib.rs. Per-start runtime creation was rejected: it would leak tasks in flight if stop() raced with start(), and would make snapshot()/drain_events() unavailable between start/stop cycles. The runtime's lifetime matches the handle's lifetime — the handle is the session. Amended 2026-06-11 (T4.1): the tokio runtime is created at open, not at start.
D8 iOS FFI is poll-based: Swift drains an event ring and reads an atomic snapshot on its own cadence. No cross-FFI progress callbacks. Callbacks from Rust into Swift across the FFI boundary require careful lifetime management and are fragile under iOS app lifecycle events (suspend/resume, background transfer limits). The poll-based design matches existing zcashlc patterns, is restart-safe (a tick after a stop/start cycle sees a clean snapshot), and avoids the thundering-herd problem of many concurrent Rust callbacks during active sync. The 2 s poll cadence (configured in Swift) is sufficient for UX progress updates.
D9 Branch: slipstream off main in this repo; mirrored slipstream branch in Zodl iOS. All commits [#1755] slipstream: <title>. main is never broken. LOCAL-ONLY: no pushes/issues/PRs to any remote until the user lifts it. User decision 2026-06-10. The LOCAL-ONLY clause was added because the prototype may not be ready for public scrutiny. Publishing a half-built sync engine to the upstream ZcashLightClientKit repository could confuse integrators and invite premature adoption. The [#1755] commit tag is a local-only marker — issue #1755 was scrubbed and closed on the remote after being created in error; GitHub never reuses issue numbers, so the tag is safe as a local identifier.

20.3 Decision Digest — major dated decisions

Upstream-brain facade pivot (T6.0, 2026-06-11)

The original P6 plan sketched injecting a custom WalletRead+WalletWrite facade at the scan_block level. Source recon falsified this: scan_block is a pub(crate)-level path; ScannedBlock and Nullifiers are not publicly constructible; BatchRunners is pub(crate). The correct injection point is put_blocks — called once per chunk by scan_cached_blocks after all scanning is done, with the write-set fully constructed. The facade overrides only put_blocks; everything else (scan, balance, PCZT) calls through to upstream unmodified. Source: STATE.md P6 T6.0 notes.

Checkpoint downgrade GO/NO-GO reversal (T6.3b, 2026-06-11)

T6.3 measured sparse-tree persistence as 4% slower than the baseline (ratio 0.96, NO-GO). The root cause was incorrectly attributed to flush I/O; it was actually upstream's checkpoint-churn algorithm — one Retention::Checkpoint per scanned block, ~10,000 per chunk, pruned back to 100 on every insert_tree call. T6.3b introduced checkpoint downgrade (pre-converting doomed checkpoints before tree insertion) and measured a 5.05× speedup (GO). The identity argument required verifying that the per-pool doomed-checkpoint cutoff equals exactly the minimum of the newest-100 retained IDs (not a simpler fixed-height cutoff), that the full pre-downgrade position maps are passed to ensure_checkpoints, and that CHECKPOINT flags do not block unite-merging. Source: STATE.md Decision Log 2026-06-11 T6.3b entry.

Counter-based progress (T5.5/T5.6, 2026-06-11)

Early progress implementations used getWalletSummary() on every tick — a blocking multi-SQL call that took 10–30 s mid-scan on A10 hardware, causing the UI to show 0% for a long time then jump. The fix decoupled progress into two counter classes (ratio vs delta, D7-extended) and moved the progress computation to cheap atomics read on every 2 s tick. The set_pass_total design stores the complete denominator atomically (not accumulated per-range, which caused a snap-back from 100% to 60% on re-suggest). Source: STATE.md Decision Log 2026-06-11 T5.6 entry.

Non-fatal interleaved enhancement (T5.6 review, 2026-06-11)

Per-range run_enhancement calls in the scheduler are deliberately non-fatal: a transient gRPC stall at a range boundary produces a warning log and continues rather than aborting the pass. The rationale: the FFI runner is single-shot (sync_once error → state Error → sync halts until app lifecycle restarts); a transient blip at an enhancement call must not abort a 16-minute A10 restore. The final post-loop enhancement backstop is the correctness guarantee; the per-range calls are a UX optimization for progressive transaction visibility. Source: STATE.md Decision Log 2026-06-11 T5.6 review.

Per-pass counter reset (T5.6 review, 2026-06-11)

Ratio counters reset at the start of each pass via begin_pass(); delta counters do not. This distinction is load-bearing for interruption-resume correctness: the handle outlives passes (prepare() opens once; stop()/start() reuse it), and Swift's lastEnhancedCount-style comparisons use strict-greater-than against a per-handle monotonic counter. Resetting delta counters would break foundTransactions emission and boundary-summary triggers on resumed passes. Source: STATE.md Decision Log 2026-06-11 T5.6 review.

Byte-budget splitting design (T6.8-S, 2026-06-12)

The sandblasting era (mainnet ~1.70M–2.00M) carries up to 2.5M outputs per 10k blocks ≈ 1 GB wire. A density-adaptive fix was chosen over a hardcoded height threshold: the ChunkSplitter in fetch.rs emits sub-chunks of at most chunk_split_bytes bytes, keyed by (plan_index, sub_index, is_last), with per-sub-chunk 120 s deadline reset and resume-from-height retry (already-emitted heights structurally cannot be re-sent). The hardcoded alternative was rejected because the spam era's boundaries are irregular, future chain events may create similar density elsewhere, and hardcoded heights are a maintenance liability. Source: STATE.md T6.8-S session log 2026-06-12.

Retry ladder tiers (T6.8-H2, 2026-06-12)

Three retry tiers exist at different granularities: (1) sub-chunk stream retries in the fetch path — worker reconnects and resumes from the last emitted height (T6.8-S); (2) scan-path treestate retries via retry_get_tree_state — 3 total attempts, reconnect on each, 1 s / 3 s backoff (T6.8-H2); (3) pass-level bounded retry in the FFI runner — PASS_RETRY_MAX=2 (3 total attempts), 5 s / 15 s sleep, only is_transient=true errors (T6.8-H2). The tiers are independent and complementary: tier 1 handles fetch-path stream stalls; tier 2 handles scan-path treestate stalls within a pass; tier 3 handles pass-level failures that tiers 1–2 could not absorb. Source: STATE.md T6.8-H2 session log 2026-06-12.

L2 seam confirmed blocked (T6.8-L3a gate, 2026-06-12)

The L2 row-batching optimization (raw-SQL multi-row INSERT into the live WalletDb transaction) was confirmed seam-blocked by source inspection: zcash_client_sqlite 0.21's WalletDb::transactionally closure exposes a private conn: C field with no public accessor (lib.rs:270). No pub fn conn(), pub fn raw_conn(), as_rusqlite(), or inner() methods exist. Resolution requires an upstream patch or a vendored fork. The estimated speedup (~8–80 s on device) justifies pursuing upstream engagement. Source: STATE.md Decision Log 2026-06-12.
