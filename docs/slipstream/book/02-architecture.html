Architecture Overview

Part I — Overview  ·  estimated reading time: 12 minutes

1-minute summary

Slipstream is layered: a platform-neutral Rust engine core (slipstream-core) sits inside the existing libzcashlc XCFramework, exposed via six C FFI functions. A Swift actor wraps that surface; a Swift Synchronizer adapts it to the app. The critical design choice is "upstream brain, Slipstream body": all cryptographic and wallet-logic decisions are delegated to unmodified librustzcash crates; Slipstream owns only the orchestration — parallelism, pipelining, and persistence scheduling.

The "upstream brain, Slipstream body" principle (D2)

The most important sentence in the entire design is Decision D2, locked in the roadmap: "upstream brain, Slipstream body." Understanding what this means precisely is the key to understanding every correctness and security claim in this book.

What the upstream brain owns (Slipstream never touches):

  • suggest_scan_ranges — the single source of truth for which blocks to scan next. Slipstream's scheduler calls this function and obeys what it returns, in priority order. It never reorders, skips, or second-guesses the result.
  • scan_cached_blocks — the upstream trial-decryption kernel. Slipstream provides blocks to it via a custom MemBlockSource; the kernel does all note scanning, nullifier computation, and tree insertion.
  • put_blocks semantics — the data contract at the boundary of the scan kernel. Slipstream may swap the implementation of this trait method (the sparse path, chapter 7), but only in a way that produces byte-identical rows — oracle-verified.
  • get_wallet_summary, fully_scanned_height — balance and progress queries. Slipstream reads these; never fakes them.
  • The entire spend path — propose_transfer, PCZT construction, proof generation. None of these are touched.
  • Account management (import_account_ufvk, list_accounts, delete_account).

What Slipstream owns:

  • How many GetBlockRange streams to open in parallel and how to split plan chunks into sub-chunks.
  • The ordering logic that reassembles parallel fetched chunks into a strict height-ordered queue.
  • The scheduling loop (when to call suggest_scan_ranges again, when to stop).
  • The put_blocks path (which may take the sparse in-memory tree route).
  • Enhancement: calling transaction_data_requests, dispatching get_transaction, and applying decrypt_and_store_transaction.
  • Transparent UTXO refresh.
  • The FFI polling surface visible to Swift.

This division means an auditor verifying correctness of note scanning, nullifier derivation, or balance computation can direct all attention to the upstream librustzcash codebase — Slipstream adds no new cryptographic logic.

The sync-pass swimlane

A single sync pass (one call to sync_once in engine.rs) proceeds through the following stages. Note that within each range loop, fetch and scan overlap.

Concurrency model

Slipstream uses two runtimes for two different kinds of work, plus a shared-memory bridge between them.

tokio — async I/O and task scheduling

Each SlipstreamHandle owns one tokio::runtime::Runtime built with 4 worker threads (configured in zcashlc_slipstream_open, rust/src/lib.rs). It lives from open to free (Decision D7, deviation from the original plan of per-start creation). All network I/O — tonic gRPC streams, get_tree_state retries, enhancement futures — runs inside this runtime.

The tokio runtime is never visible to Swift. The Swift actor (SlipstreamEngine) serialises all calls to the six C FFI functions; the runtime's threads are internal to the Rust handle.

rayon — CPU-bound tree parallelism

The sparse persistence path in persist.rs uses rayon::join to process the Sapling and Orchard commitment trees in parallel for each chunk. This is the L3a optimization (T6.8-L3a). Both closures run on the rayon thread pool (the tokio worker thread calls rayon::join via block_in_place).

Within each per-pool tree operation, rayon::par_chunks is used inside build_subtrees (upstream code). This nesting is safe: rayon's work-stealing pool allows nested par_chunks on available threads.

Progress — lock-free polling (D8)

All progress data visible to the Swift polling layer is read from Arc<Progress> in events.rs — a struct of 9 AtomicU64 fields. No lock is held to read a snapshot. The fields are written by the Rust sync task and read by the Swift polling loop (every 2 seconds) without any cross-FFI callbacks or notification mechanisms.

This poll-based design (Decision D8) was chosen for simplicity and restart safety: if a sync pass is cancelled and restarted, the polling loop simply continues reading from the same atomics. No callback registration / deregistration is needed, and no cross-FFI liveness issue can arise.

Note on counter resets

Progress counters are split into two classes. Ratio counters (scanned_blocks, fetched_blocks, pass_total_blocks, current_range_end, spendable_hint) are reset by begin_pass() at each sync_once entry — including on pass-level retries. Delta counters (enhanced_txs, ranges_completed, reorgs_recovered) are monotonic per handle and never reset within a handle's lifetime; the Swift layer detects changes by strict-greater comparisons. This split is load-bearing for interruption-resume correctness (Decision Log, 2026-06-11).

Event ring

A 64-event circular buffer in ffi_handle.rs carries typed events from the Rust sync task to the Swift polling loop. Tags: 1=SyncStarted, 2=SyncProgress (unused), 3=SyncDone (value = tx count), 4=SyncError (value = error code), 5=FoundTransactions. The ring is drained atomically — a single Mutex<Vec> lock covers the entire drain operation. Overflow drops the oldest event.

Panic containment (B1)

Tokio swallows panics inside spawned tasks — they surface only through the JoinHandle, which was not previously inspected. A panicking pass would die silently, leaving state stuck at "Syncing" forever (field failure 2, 2026-06-12). The fix is a supervisor task (spawn_supervised in ffi_handle.rs) that owns the sync task's JoinHandle and converts a panic JoinError into SyncState::Error(2) + a tag=4/value=2 event. Cancellation (from stop()/free()) is deliberately ignored — the caller already sets state.

The FFI boundary

Six C functions in rust/src/lib.rs are the entire Slipstream-to-Swift contract:

FunctionContract
zcashlc_slipstream_openAllocates a SlipstreamHandle (tokio runtime + atomics + event ring). Returns an opaque pointer or null on failure. Installs the panic tracing hook.
zcashlc_slipstream_startCancels any in-flight task, spawns a new supervised sync task. Returns true on success. UFVK is optional (null = keyless/update-only). Emits SyncStarted exactly once, even across retries.
zcashlc_slipstream_stopAborts the in-flight task and sets state to Idle (non-blocking). Returns immediately. Poll snapshot to confirm.
zcashlc_slipstream_snapshotNon-blocking point-in-time read of all AtomicU64 progress fields + state. Zero-filled on null handle.
zcashlc_slipstream_drain_eventsAtomically drains up to buf_len events into a caller-allocated buffer. Returns count drained. Drained events are removed from the ring.
zcashlc_slipstream_freeAborts any in-flight task, drops the handle (drops the tokio runtime). After this call, the pointer must not be used.

Known limitations

Architecture-level gaps
  • In-foreground tip-following (DONE, T8.1): sync_once runs one complete pass, after which sync_body enters a jittered 10–30 s probe loop and launches a keyless catch-up pass whenever the server tip advances (cancelled by the AbortHandle on stop/free). The pass-level retry loop (T6.8-H2: up to 3 total attempts for transient transport errors, sleeping 5s/15s between attempts) remains bounded — it does not loop indefinitely.
  • Tor wired (DONE, T-Tor): when the host enables Tor, the engine bootstraps its own arti client; grpc.rs routes wallet-identifying calls (treestate, latest-block, getInfo, GetTransaction, transparent txids/UTXOs, submit) over isolated Tor circuits while the bulk GetBlockRange download stays direct — mirroring the old SDK's per-call policy. See chapter 15.
  • L2 row batching seam-blocked: the put_blocks SQL write path inside zcash_client_sqlite cannot be replaced via public API without a fork or upstream PR — the performance lever for bulk-inserting rows exists but is blocked at the library boundary.
  • L4a decrypt kernel parked: a column-oriented ECDH scan kernel would eliminate the 3–5% decryption fraction and could cut further into the tree-time overhead on modern hardware, but requires a new oracle harness (the current oracle covers the scan_cached_blocks output, not an alternative kernel). Deferred.
