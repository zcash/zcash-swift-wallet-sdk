6. Scan Pipeline

Estimated reading time: 12 minutes

1-minute summary

The scan pipeline drains the ChunkQueue one sub-chunk at a time, passing each to the upstream scan_cached_blocks kernel via a thin MemBlockSource adapter. Each scan call requires a server-side treestate at the chunk boundary; the pipeline prefetches the next boundary's treestate concurrently with the blocking scan, hiding network latency. Prefetches use transient-error retries (up to 3 attempts, reconnect on each) to survive the stall pattern observed in the field. Sub-batching (opt-in) splits a chunk into time-targeted pieces for slow devices but defaults off because the fixed overhead exceeds gains on modern hardware. An enhancement interleave fires every K completed chunks (default K=3) to surface transactions progressively. Continuity errors (reorgs) are mapped to a structured ScanContinuity error that the scheduler recovers from without losing context.

One-chunk-per-scan_cached_blocks: the memory rule

Each call to scan_cached_blocks processes exactly one sub-chunk from the ChunkQueue. This one-to-one mapping is the fundamental memory bound of the scan pipeline: the engine never holds more than one chunk's worth of decoded block data in the scan kernel simultaneously. The scanner holds the chunk's ChunkPermit (and therefore its byte-budget allocation) for the duration of the call, releasing it only after the final sub-batch of that chunk has been committed to the database (scan.rs:349).

The corollary is that the scan pipeline and the fetch pipeline share exactly the ChunkQueue's byte budget (256 MiB). If the scanner falls behind, the ChunkQueue fills up and the fetch workers stall at the ChunkQueueSender::send semaphore — natural backpressure, no explicit coordination needed.

MemBlockSource

scan_cached_blocks requires a BlockSource trait implementation to provide blocks. Slipstream's implementation is MemBlockSource (block_source.rs): a thin wrapper around an in-memory Chunk that serves each block on demand. It holds a reference to the chunk, not a copy — no additional allocation is required. The wrapper satisfies the upstream API contract exactly; the scan kernel sees the same interface it would from a SQLite-backed block cache in the old SDK.

Treestate threading: the from_state invariant

scan_cached_blocks requires a ChainState (the server's view of the Sapling and Orchard commitment trees at the block immediately before the scan range) that satisfies:

from_state.height() + 1 == from_height

Slipstream maintains this invariant at every scan call boundary. The initial seed is fetched at range_start - 1 before the first chunk. At each subsequent boundary (whether a sub-batch boundary within a chunk or a whole-chunk boundary), the state is fetched as the end height of the previous batch and becomes the from_state for the next call. The proof, from scan.rs:246–258:

  • For the first sub-batch of the first chunk: next_state was fetched at range_start − 1; sub_start = chunk_start = range_start. Height matches: (range_start − 1) + 1 = range_start.
  • For any subsequent sub-batch: next_state was fetched at sub_end of the previous sub-batch; new sub_start = prev sub_end + 1. Height matches: sub_end + 1 = sub_start.
  • For the first sub-batch of subsequent chunks: next_state was fetched at the previous chunk's end height; chunk_start = prev_chunk_end + 1. Height matches.

Prefetch overlap: hiding treestate latency

Fetching a treestate from lightwalletd takes 100–500 ms on a mobile connection (the call goes to the same server handling block downloads). Without prefetching, the scan pipeline would stall at every chunk boundary waiting for the next GetTreeState call to complete.

The prefetch pattern spawns a Tokio task for the next boundary's treestate before entering the blocking scan call, then awaits the result after the scan returns. On fast hardware where the scan takes longer than the treestate fetch (the common case), the prefetch completes before the scan does — zero latency added at the boundary. On slow hardware where the prefetch outlasts the scan, the pipeline waits only for the difference:

// scan.rs:233–236 — spawn the prefetch before the blocking scan
let prefetch = tokio::spawn({
    let ep = endpoint.clone();
    async move { grpc::retry_get_tree_state(&ep, sub_end, "chunk-boundary prefetch").await }
});
// ... blocking scan runs here (block_in_place) ...
// scan.rs:310–311 — await the prefetch result after the scan
let fetched = prefetch
    .await
    .map_err(|e| SlipstreamError::Transport(format!("prefetch task: {e}")))??;
next_state = fetched;

On scan failure, prefetch.abort() is called before returning (scan.rs:288) — the detached task would complete harmlessly either way, but aborting it avoids a wasted gRPC call.

Treestate retry (T6.8-H2)

A field failure (2026-06-12, STATE.md T6.8-H2 session log) showed the engine dying after a successful scan because the prefetch for the next boundary timed out in exactly 30 seconds with no retries: transport: get_tree_state: timed out after 30s. The fix uses grpc::retry_get_tree_state in both the initial seed and the per-boundary prefetch spawns — up to 3 total attempts with 1 s then 3 s backoff, reconnecting on each attempt (scan.rs:169 and scan.rs:235). Non-transient errors (decode failures, protocol errors) propagate immediately without retrying.

Field evidence — T6.8-H2 failure, 2026-06-12

A real wallet restore reached chunk 3,361,166 (scanned cleanly in 3.77 s), then the chunk-boundary treestate prefetch timed out after 30 s with a single attempt. The sync died at 6.1% with no recovery. After shipping retry_get_tree_state, the mainnet tip−2000 oracle run (STATE.md T6.8-H2 session log) passed cleanly with VERDICT IDENTICAL across all 26 tables.

Sub-batching: opt-in and why it defaults off

Sub-batching (EngineConfig::scan_batch_target_ms) splits each chunk's scan into time-targeted pieces via a proportional controller (scan.rs:52–64). The default is None (off). The performance history explains why:

DeviceEffect of sub-batchingVerdict
A10 iPad (field)Each sub-batch boundary pays ~1.5–2s of fixed put_blocks overhead (a fresh checkpoint set + tree commit per sub-batch). Splitting a 10k-block chunk into 3–4 sub-batches adds 4–6s per chunk vs a single call.No gain; net loss.
M-series Mac (bench)Sub-batches complete instantly at the default 3s target; the controller immediately returns max = chunk_len. Equivalent to no sub-batching.No effect.

Sub-batching was designed for a time before the sparse-persistence path (chapter 7) reduced the per-chunk tree cost by ~5×. With sparse trees, each chunk already commits quickly enough that sub-batching's "finer progress updates" benefit does not compensate for its overhead. It remains available as an explicit opt-in for use cases where extremely slow scan devices need sub-second DB commits.

Evidence basis

The A10 field observation is from STATE.md T5.2 session notes (2026-06-11): "each sub-batch pays ~1.5–2s fixed cost (put_blocks shardtree overhead, measured on A10 iPad)". The controller unit tests in scan.rs:517–608 cover the proportional rule and its edge cases but do not validate device-specific performance.

Per-K-chunk enhancement interleave (T6.1)

Enhancement (fetching full transaction data) normally runs at range boundaries and at the end of the pass. Waiting for a large range to complete before surfacing transactions can mean several minutes of "scanning" with no transaction visibility. The interleave fires run_enhancement every K completed chunks (default K=3, configured via EngineConfig::enhance_every_chunks):

// scan.rs:355–370 — interleave cadence check
if should_interleave_enhancement(stats.chunks, config.enhance_every_chunks) {
    let started = Instant::now();
    let mut enhance_client = client.clone();
    match run_enhancement(session, &mut enhance_client, network, ...).await {
        Ok(es) => { stats.interleaved_enhance.txs_stored += es.txs_stored; ... }
        Err(err) => { warn!(%err, "interleaved enhancement failed — continuing scan"); }
    }
    stats.interleaved_enhance_elapsed += started.elapsed();
}

Two design choices are load-bearing:

  1. Non-fatal: a failed interleaved run logs a warning and continues scanning. The per-range and final post-loop enhancement runs are the correctness backstops. An interleaved transport failure must not abort a multi-minute restore.
  2. Elapsed excluded from scan time: stats.interleaved_enhance_elapsed is subtracted from the scan-stage wall time in the scheduler's report (scheduler.rs:293). Stage-split logging in the CLI and device logs therefore attributes enhancement time to the enhance stage, not the scan stage.

The should_interleave_enhancement helper (scan.rs:71–73) is a pure function: it returns true when chunks_done > 0 and chunks_done % every == 0. Never fires before the first chunk completes.

Continuity error mapping

When scan_cached_blocks returns a ChainError::Scan(err) where err.is_continuity_error(), it means the blocks being scanned do not continue from the wallet's current chain tip — a reorg has occurred. The map_scan_error function (scan.rs:87–99) converts this to a structured SlipstreamError::ScanContinuity { at }, where at is the block height of the continuity break.

The scheduler receives this error, truncates the wallet to at.saturating_sub(10), and re-suggests scan ranges — exactly mirroring the upstream recovery path. For the full reorg story, see chapter 10.

Known limitations

Honest gaps
  • Sub-batching overhead not re-measured since sparse path: the decision to leave sub-batching off by default was made before the 5× sparse-tree speedup (T6.3b). It is plausible that sub-batching's per-sub-batch cost is now smaller than originally measured, but no A10-device A/B has been run with sparse trees + sub-batching enabled. The default-off decision is conservative and correct.
  • Treestate trust: server-provided treestates are used as from_state without independent verification before the scan. A compromised lightwalletd can provide a malicious treestate; the scan kernel will then compute incorrect note positions. This is the same trust model as the old SDK and is documented in chapter 14.
