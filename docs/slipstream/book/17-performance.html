1-minute summary

Every performance number in this book comes from a single source: the truth table in STATE.md, with machine, server, range, wall-clock, and bound recorded for each row. This chapter reproduces those rows verbatim, explains how to reproduce any run with the CLI, describes the stage-split instrumentation and per-chunk attribution that make the numbers trustworthy, and recounts the stale-framework incident that added the ENGINE_BUILD freshness tag. 17.1 Measurement discipline

A rule that pre-dates every number in this chapter: every performance claim earns a row in the truth table. The five required columns are:

ColumnWhat it recordsWhy it matters
Machine / deviceHardware model or OS identifierMac numbers do not extrapolate to A10 devices; iPhone 16 Pro numbers do not extrapolate to A10 iPads

Wall-clockTotal elapsed time and stage breakdown where availableAbsolute time is the user-visible metric; stage split locates the bottleneck
BoundWhich stage limited throughput: network, scan, or enhanceWithout this, a fast fetch looks like a fast scan
Benchmarks as CLI subcommands

Every performance run is reproducible via slipstream-cli. Two subcommands: fetch --range A..B --streams K --chunk N measures parallel download throughput (the G1 rows below); sync --server URL --wallet-dir DIR --ufvk UFVK --birthday H runs a full end-to-end sync (all later rows). Stage-split is printed in the final summary line. This design means any session can reproduce any row from the truth table — no bespoke scripts, no ad-hoc timing.

The stale-framework incident and the ENGINE_BUILD tag

On 2026-06-12, a device field run produced numbers consistent with T6.6 performance rather than the freshly-built T6.8-L3a build. The diagnosis: ./Scripts/rebuild-local-ffi.sh replaces only one architecture slice by design. After that, other-platform Xcode builds silently reuse the old-slice copy at the top of the XCFramework. The device ran the previous engine. Nine minutes of wall-clock time — attributed to the wrong build.

The fix is the ENGINE_BUILD constant in slipstream/core/src/engine.rs:25:

pub const ENGINE_BUILD: &str = "2026-06-13.walltime";

Every sync start and stage-split log line carries this tag. A device log whose tag does not match the expected value means the old binary is running — stop, run ./Scripts/init-local-ffi.sh (all three slices), reset SPM caches in Xcode, rebuild. The freshness probe command is:

strings <slice>/libzcashlc.framework/libzcashlc | grep <expected-tag>

The tag is bumped on every performance-relevant engine change. It is the single check that catches stale binaries when the header looks fine.

17.3 Stage-split anatomy

Stage-split instrumentation was added in T5.1 (P5 phase). Every sync_once completion emits a structured log line:

engine sync stage split
    total_s=NNN fetch_s=NNN scan_s=NNN enhance_s=NNN
    blocks=NNN sparse=true engine_build=2026-06-13.walltime

The ENGINE_BUILD tag appears in every stage-split line. A log without the expected tag means a stale framework ran.

Within each scan chunk, the sparse path additionally emits per-pool attribution:

sparse put_blocks chunk=N
    rows_ms=NNN tree_ms=NNN flush_ms=NNN downgraded=NNNN
sparse orchard tree split chunk=N
    downgrade_ms=0 build_ms=NNN frontier_ms=NNN insert_ms=NNN ensure_ms=0
sparse sapling tree split chunk=N
    downgrade_ms=0 build_ms=NNN frontier_ms=NNN insert_ms=NNN ensure_ms=0

The per-pool split was added in T6.8-L3b and is emitted by all production builds. Future device logs carry the device's own sub-split without any additional instrumentation.

17.4 How to reproduce a run

Fetch benchmark (CLI)

cargo run -p slipstream-cli --release -- fetch \
  --server https://zec.rocks:443 \
  --range 3200000..3250000 \
  --streams 4 \
  --chunk 10000

This reproduces the G1 canonical K=4 rows. Change --streams 8 and --chunk 5000 for the K=8 series. Ratio variance of ±1× is normal due to server-side throttling — record multiple runs.

Full sync (CLI)

cargo run -p slipstream-cli --release -- sync \
  --server https://zec.rocks:443 \
  --wallet-dir /tmp/my-sync-wallet \
  --ufvk <TEST_UFVK> \
  --birthday 3324467 \
  --sparse true

The engine prints a stage-split summary at completion. Verify engine_build=<current-tag> in the output before recording numbers.

Oracle A/B comparison

cargo run -p slipstream-cli --release -- oracle \
  --server https://zec.rocks:443 \
  --wallet-a /tmp/t64-oa \
  --wallet-b /tmp/t64-ob \
  --sparse-b \
  --ufvk <TEST_UFVK> \
  --birthday 3324435

Runs Path A (upstream) and Path B (sparse Slipstream) against the same range, then prints VERDICT IDENTICAL or a diff table. The oracle CLI is the correctness gate; the performance numbers come from the scan_s values the same run emits.

17.5 What the numbers do not prove

Honest limitations
  • The iPad A10 8:30 (T6.7b) result was achieved with manual server selection to avoid the AutoServerSelection restart cost. The automatic-server result was 9:21. This distinction is preserved in the truth table and must not be collapsed.
  • All Mac numbers are on a darwin 25.5 MacBook with M-series silicon. They do not extrapolate to A10-class (2-core, 2 GB RAM) devices.
  • Server load on zec.rocks varies. Fetch ratios ranging from 1.06× to 3.86× in the same G1 series prove this. Any single-run fetch ratio is not a stable benchmark.
  • The sandblasting acceptance (8.9k blk/min) was measured on Mac. A10-class device memory budgets for the spam era (1.7M–2.0M) are an open blocker — see ch. 19.
